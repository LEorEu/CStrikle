### v1 修过的两处错（`blinddraft/match.py`，已删除）

留着这一节是因为这两条结论对 v2 仍然成立，v2 是照着改后的语义写的：

- **Carry Hierarchy 由卡面定死。** 火力聚合的 `.35 / .25 / .133×3` 以前按
  **当图掷骰结果**重排，等于一次高 Roll 拿两次奖励——自己涨分，还从后排跳到
  主枪位。实测低火力队友能在 12.7% 的图里挤掉 donk。注意这条**几乎不改变
  胜负**（队伍强度均值只差 0.03~0.71 分），它修的是语义。
- **MVP / LIFE GAME / UNDERPERFORM 三个口径拆开。** 旧 `mvp` 只从**赢家一方**
  取 `eff - base` 最大的人，两个后果：输掉的一方永远无人上榜（「核心尽力了、
  队友带不动」讲不出来），而比超常幅度系统性奖励低卡面高波动的人——实测
  spaze(F50) 的 MVP 率 24.3% 反超 donk(F96) 的 19.5%，donk 的 LIFE GAME 率
  恒为 0。现在 MVP 看**最终有效火力、两队合评**，另外两个看偏离。改完 donk
  的 MVP 率 87.3%，spaze 0.0%。

阈值取 `LIFE_GAME_AT = 12`（不是复盘建议的 10）：12 的触发率已接近每四张图
一次，再往下调就变成常态了。

每张图还会给出**十个人的逐人账本**：`delta` 拆成「全队状态 + 个人状态 +
指挥挽回 + 经验挽回 + 软顶」，逐项可加，测试断言无残差。Leadership 在队伍
层面的做功也直接给出（救回的火力按 Carry 权重折算）——它只在负 Roll 时生效，
全队手热的那张图它的贡献精确等于 0。

**v1 没有解决的**：Entry 是 `40% 火力 + 20%×3` 的静态聚合，Stability /
Experience 因此被算两遍；`soft_cap` 单向压制高火力选手。这两条是架构问题，
v2 解决了（Entry 纯火力、soft_cap 关掉）。

那份逐人账本的拆法在 v2 里变了：§11 退役了 Team Shared Form，Leadership 也不再
逐人挽回，所以现在是「个人状态 + 压力多丢的分 + 软顶」三项，仍然逐项可加、
测试断言无残差。

### v2（`blinddraft/engine/`）

实现 v0.3 §15 的 Pipeline。当初做成独立原型而不是就地改 v1，所以它不 import
`match.py`；v1 退役时因此不用拆任何依赖，直接删掉即可，事实也是这么发生的。

```powershell
python -m blinddraft.engine --lab       # 六项验收
python -m blinddraft.engine --tune      # MAP_SCALE 扫描
python -m blinddraft.engine --compare   # 和 v1 的胜率曲线对比
python -m blinddraft.engine --demo "donk carry"
python -m blinddraft.engine --field     # 32 席怎么来的
python -m blinddraft.engine --major "donk carry"   # 跑完整一届
python -m blinddraft.engine --audit     # VRS × Entry 偏差审计
python -m blinddraft.engine --audit-cards          # 谁的四维是猜的，逐队逐人
python -m blinddraft.engine --audit-cards --thin-only   # 只要两张待办名单
```

**一张图 11 个随机数**：10 个 Player Performance + 1 个 Map Residual。没有
Team Shared Form（§12 退役），没有独立 Choke 骰（§8.3），没有最终 Bernoulli
胜负骰（§13）。四维各做一件事：Firepower 定基线、Stability 定兑现分布、
Experience 只在 Pressure>0 时扭曲同一次 Roll、Leadership 只做 Team Execution。

Entry 是纯火力口径（≈80），**和 v1 的 ≈65 不可直接比较**。

**系数都有出处，没有一个是拍的。** Stability 分布和 Choke 幅度从设计稿举的
例子反推，实测复现：F80/S90 落 75~90、F80/S50 落 63~98；「新人 −7 经验25
生死局 → −11、老将 −7 经验90 → −7.5」。Leadership 则按 §9.2 的新规矩，先定
胜率目标再反推 Strength。

### MAP_SCALE 定 6，但它不是胜率曲线

§13.3 让扫 4/5/6/7，实测（`--tune`）：

| SCALE | +2 | +5 | +10 | +20 | +10 时 BO1 爆冷 |
|---:|---:|---:|---:|---:|---:|
| 4 | 59.2% | 72.7% | 88.7% | 98.8% | 11.3% |
| **6** | **56.7%** | **67.0%** | **81.2%** | **95.9%** | **18.8%** |
| 7 | 55.5% | 65.1% | 78.0% | 93.6% | 22.0% |
| 9 | 54.5% | 62.4% | 72.9% | 88.9% | 27.1% |

6 让四条验收目标同时满足。旧 `WIN_SCALE=13` 确认不迁移——那会让 +10 只剩
68%，选手层重新被宏观随机淹没。

**要订正设计稿 §13.3 的一句话。** 它说 Map Residual 与经典 logistic 胜率
「统计意义上等价」——这只在「双方 Team Performance 是常数」时成立。实际 SA、SB
各含 Player 波动（两队之差 σ≈4.3），Residual 自己 σ≈10.9，最终曲线是两者的
**卷积**：

| 火力差 | 实测（整套） | logistic(gap/6) | 反解等效 scale |
|---:|---:|---:|---:|
| +2 | 57.0% | 58.3% | 7.06 |
| +5 | 67.5% | 69.7% | 6.83 |
| +10 | 81.8% | 84.1% | 6.66 |
| +20 | 95.8% | 96.6% | 6.40 |
| +30 | 99.1% | 99.3% | 6.36 |

等效 scale 不是常数，随分差从 7.1 漂到 6.4——所以整条曲线连 logistic 形状都
不是，谈不上把 MAP_SCALE「换算」成胜率。

> **MAP_SCALE 只控制 Residual 那一层。任何胜率结论都必须靠 Monte Carlo 实测，
> 不能由它解析推导。**

这条对所有队伍层 modifier 都成立：§9.2 那个「先定胜率差再反推 Strength」的
规矩，反推用的换算率（当前 1 分 ≈ 3.5 个百分点）本身就是跑出来的，而且
MAP_SCALE 一动就得重跑。

#### 修掉一个 v1 至今仍有的问题：VRS 分层被忽略

`build_current_field` 给每支队标了 `regional_stage`，但 v1 的 `run_major` 是按
Entry 排名切 `field[0:8] / [8:16] / [16:32]`，那个字段**算出来没人用**。实测
32 支里 13 支对不上：

| | VRS 排名 | v1 Entry | 区域名额给的 | v1 实际进的 |
|---|---:|---:|---|---|
| FUT | 4 | 59.8（第 22） | Stage 3 直邀 | **Stage 1** |
| Legacy | 6 | 65.1（第 12） | Stage 3 直邀 | Stage 2 |
| FlyQuest | 51 | 61.6（第 16） | Stage 1 | **Stage 2** |

§1.2 把区域名额表写死了（EU 8/6/6、AM 5/1/2、AS 3/1/0），所以 v2 里
**Stage 归属听 VRS，Entry 只排 Stage 内的种子**。两把尺子各管各的：VRS 回答
「凭什么拿到这个席位」，Entry 回答「同一层里谁更强」。

**v1 没改**，它还在服役、`/play` 还在用它，改了会动现有行为。这一条记在这里，
等 v2 接管时一起过去。

#### 玩家的 Stage 用哪把尺子

玩家是临时组的队，没有 VRS 积分，能衡量他的只有 Entry。所以：

> AI 的 Stage 由区域 VRS 名额定；玩家的 Stage 由 Entry 的**全场排名**定
> （前 8 进 Stage 3、9-16 进 Stage 2、其余 Stage 1），然后名额守恒逐级级联。

一开始试过「逐层挤」——Entry 高过某层最弱的就进那层。实测不成立：两把尺子的
秩相关只有 0.63，层间 Entry 重叠得很厉害（本届 Stage 2 最弱的 BIG 只有 61.5，
Stage 1 最强的 Astralis 有 81.4），那样一支 62 分的队能挤进 Stage 2 却比
Stage 1 半数队都弱。已改掉，回归测试盯着这条。

定下 Stage 之后仍然逐级级联：该层最弱的掉一级，下一层多一支、最弱的再掉一级，
Stage 1 多出来的那支失去席位。v1 那句「你的加入让下面几支各降一级」的叙事保住了。

#### 压力分四档

v1 只有三档（BO1 0 / BO3 1.0 / 生死局 1.25）。v0.3 §8.1 要求 Format 和 Pressure
分开，所以 v2 是：

| 局面 | 赛制 | 压力 |
|---|---|---:|
| 普通轮次 | BO1 | 0.0 |
| 2 胜，赢了就晋级 | BO3 | 0.8 |
| 2 负，输了就淘汰 | BO3 | 1.0 |
| 2-2 生死局 | BO3 | 1.2 |

赢一场就出线和输一场就回家，不该给同一个数。

#### 整届跑出来的分布

同一套阵容换 200 个 seed：

| 阵容 | Entry | 进场 | 进 Playoffs | 平均胜场 |
|---|---:|---|---:|---:|
| donk carry | 79.9 | Stage 2 | 20.5% | 4.54 |
| 五个普通职业哥 | 62.3 | Stage 1 | 0.0% | 1.58 |

弱队从 Stage 1 起步的分关晋级率（400 届）：Stage 1 过 11.2%，进了 Stage 2 之后
0/45。按单场胜率反推，连过两关的期望是 2.6 次，实测 0 次落在 p=6.6% 内，不是
bug——一支垫底队要连过两个 Swiss 本来就该很难。要放宽只有一个旋钮：MAP_SCALE。

### VRS × Entry 偏差审计

```powershell
python -m blinddraft.engine --audit
```

复盘（`讨论/2.txt`）纠正了上一轮一个说法：**FUT 那种「VRS 高、Entry 低」本身不是
bug。** 两把尺子回答的是不同问题——VRS 是「现实里已经挣到什么位置」，Entry 是
「今天这五个人有多能打」。刚换人、状态暴跌、积分还没掉下来，都会让两者背离。
v1 真正的 bug 只是把 VRS 分好的 Stage 算出来又扔掉，那个已经修了。

所以现在不追求把两条曲线拟到一起，只做审计，逐支回答一个问题：

> 这个偏差是**现实原因**（刚换阵容、近期爆发、排名滞后 → 保留），
> 还是**数据/模型原因**（漏人、角色识错、当前统计没覆盖、fallback 太低 → 修 Entry）？

每行带火力证据的构成，所以两类一眼能分开：

| 队 | VRS位 | Entry位 | Δ | Entry | 五人火力证据 | 判断 |
|---|---:|---:|---:|---:|---|---|
| BIG | 14 | 28 | −14 | 61.5 | 弱/回退4 IGL1 | **数据问题** |
| M80 | 31 | 19 | +12 | 74.9 | 中4 IGL1 | 证据尚可 |
| Astralis | 20 | 9 | +11 | 81.4 | 强4 IGL1 | **现实原因**：真在起飞 |
| GamerLegion | 24 | 13 | +11 | 78.3 | 强2 中2 IGL1 | 证据尚可 |

BIG 查下来是 5E 样本覆盖不足：四名首发的 `map_count` 都是 **23**，卡在 30 图
门槛之下，于是全部回退到「生涯先验 + 年龄衰减」，火力被压到 52~61。它的 Entry
低不是因为它真的弱，是因为我们没数据。Astralis 相反，四人 108~161 图的强证据，
所以 Entry 高而 VRS 滞后是真实现象，**不要动**。

修 BIG 需要重抓 5E，不在这一轮范围。

### Entry 只有一个定义了

以前有两个东西都叫 Entry：`major.entry_rating()` 是 v1 口径（火力 40% +
L/E/S 各 20%，量纲 ≈65），`engine.Team.entry()` 是纯火力（≈80）。
比赛只读后者，但 `/ai`、`ai_teams`、`major` 的赛场列表显示的是前者。

不只是数字不同，**名次也不同**，最多差 15 位：

| 队 | VRS | 旧 Entry | 旧位 | 新 Entry | 新位 |
|---|---:|---:|---:|---:|---:|
| FUT | 4 | 59.8 | 22 | 83.4 | **7** |
| PARIVISION | 16 | 56.9 | 26 | 78.2 | **14** |
| FlyQuest | 51 | 61.6 | 16 | 69.8 | **25** |

所以在 `/ai` 上 FUT 是全场第 22 的弱队，进 `/play` 打它是第 7——两个页面对同一
支队给出相反的结论，哪怕代码都没错。

**旧的那个直接删了，不是改名。** 它没有第二个来源：查下来 v2 的 Entry 就是
`draft.score()` 里那个 `fire` 项（同一组 .35/.25/.40 Carry 权重、同一条无狙
−4），只是不再乘 L/E/S 那三项。所以复合值删掉不丢信息。

- `engine.entry_of(roster, chem, adjust)` 是**唯一**定义；
- `major.entry_rating()` 只剩磨合度（`chem_raw` / `cohesion`），不再产出
  `base` 和 `entry`——磨合度是赛前就定死的先天量，仍然归赛场层；
- `major.Entry.entry`、`ai_teams.entry_of()` 都改成调那一个函数。

`OneEntryDefinitionTests`（3 项）盯着这条：`entry_rating` 不许再返回 `entry`
或 `base`、`/ai` 显示的必须逐队等于 `/play` 里上场的、L/E/S 改成任何值 Entry
都不许动。

### 火力门槛从 30 图降到 10 图

`--audit` 回答「哪支队的 VRS 和 Entry 对不上」，`--audit-cards` 回答上一层的
问题：**那 32 支队里有多少人的四维根本没有当前证据**。两个一起看才分得清
「它真的弱」和「我们不知道它多强」。

```powershell
python -m blinddraft.engine --audit-cards              # 总览 + 逐队 + 逐人
python -m blinddraft.engine --audit-cards --thin-only  # 只要两张待办名单
```

第一次跑出来的数比预期难看：**正赛 160 席里 37 人（23%）的火力没有任何当前
证据**，全部回退「生涯先验 + 年龄衰减」。而且不是均匀分布的——七支队各有
3~4 名首发是猜的（BIG、Alliance、HOTU、JiJieHao、DENDELE、FlyQuest、magic），
其余 25 支最多 2 人。VRS 名次比 Entry 名次高 8 位以上的队**全部**出自这七支，
反向偏差（Astralis +11、GamerLegion +11、M80 +12）则证据齐全。「数据问题」和
「真在起飞」在数据上本来就是分开的两类。

原因是 30 图那道门槛。BIG 四名首发全卡在 **23 图**、magic 三人 27 图、
HOTU 三人 22 图、FlyQuest 三人 21 图——差一点点，然后整个人退回三年前的生涯卡。

**改法：火力门槛 30 图 → 10 图**（`FIRE_MIN_MAPS`，硬门槛，低于它直接回退）。
S 级 9 张图就是打满三个 BO3，10 张图约四场比赛；样本确实会失真，但把 rating
整个丢掉、退回生涯先验，失真更大。10~79 图之间照旧按 `SHRINK_MAPS` 向先验
收缩，图越少越靠先验。

| | 改之前 | 改之后 |
|---|---:|---:|
| 正赛无当前火力证据 | 37 人（23%） | **11 人（7%）** |
| 3 人以上无证据的队 | 7 支 | **2 支**（JiJieHao、Alliance） |
| 秩相关 ρ（VRS × Entry） | 0.763 | 0.760 |

Entry 只对那五支数据饥饿的队动了：HOTU +6.7、magic +5.7、BIG +5.6、
DENDELE +4.0、FlyQuest +2.8，其余 27 支一分未动。**名次几乎没变**，而这正是
最有价值的一条结论：

> BIG 的 Entry 从 61.5 升到 67.1，仍然是第 28。它五名首发的 rating 就是
> 0.97~1.04。所以 BIG 排在这里不再是「我们没数据」，而是**当前证据就是这样**。
> `--audit` 那一行也跟着从「弱/回退4 → 数据问题」变成「中4 → 证据够」。

### `map_count` 是 Evidence Confidence，不是 Stability

同一轮里试过第二条改动：把出场量接到 Stability 上（图少 → 扣稳定值），理由是
「打不进 S 级赛事本身就说明兑现率低」。**实测不能要，已撤回。**

那是对同一批人罚两次：数据少已经让他们的火力被拉回先验，再削稳定值，弱队
既更容易失常、分布又更宽，净效果是**爆冷变少**——实力差 10~15 时 BO1 强队
胜率从 86.6% 涨到 91.9%。而爆冷正是这类队在游戏里唯一的存在感。

> 一支队打得少是**我们的认知问题**，不该变成它在比赛里的惩罚。

所以样本量只做一件事：决定火力那一维信不信当前证据。Stability 仍然只有生涯
先验一个来源，KAST 也依旧不许用来生成它（聚合 KAST 不是逐图方差）。
`EvidenceConfidenceTests`（4 项）盯着这条不要被「听起来有道理」地加回来。

**还没解决的**：卡库外真人（正赛 26 人，16%）的 Leadership / Experience 仍然
是角色模板常量。火力这一维现在有救了，那两维没有任何数据源，得先决定从哪来。
`--audit-cards` 最后一张表专门列它们。

### 一个意外收获：v2 的 Entry 和现实排名更吻合

32 支正赛队，VRS 排名与我们的 Entry 的秩相关：

| Entry 口径 | ρ |
|---|---:|
| v1（火力 40% + L/E/S 各 20%） | 0.631 |
| **v2（纯火力）** | **0.763** |

拿掉 L/E/S 的静态权重反而离现实更近了。FUT 是最清楚的例子：v1 口径下 Entry
59.8（全场第 22），v2 口径下 83.4（第 6），VRS 是第 4。之前那个「13 支队进错
Stage」里有相当一部分其实是 v1 的 Entry 口径自己造成的。

README 里记的 0.633 是 v1 的数，仍然有效，只是现在有了对照。

### TODO：玩家的 Stage 判据仍是临时规则

现在是「Entry 全场排名 → 8/16/32」。它明显好过最初的逐层挤，但架构上仍然有
两套判据并存：真实队走 VRS，玩家走 Entry。

`讨论/2.txt` 给了正确的长期方向——引入第三个概念 **Projected / Synthetic VRS**：

```text
真实队：Current VRS + 由 Entry 预测的有界变动 -> Projected VRS -> 区域 cutoff -> Stage
玩家：  Entry percentile -> Synthetic VRS      -> 区域 cutoff -> Stage
```

叙事是「假定你的梦之队在邀请截止前已经打了一段未展开模拟的资格竞争」，这比
「因为你 Entry 全场第 12，所以判你 Stage 2」自然得多。

**这一轮没做**，因为第一版的底层仍然是 Entry percentile，做出来数值上和现在
完全等价，只是换了个名字——那样容易让人以为 Projected VRS 已经实现了。等到
真的要做真实队的 VRS 变动预测时，两件事一起做才有意义。

同样标着的还有：Stage 内的种子现在按 Entry 排，追求真实 Major 语义的话应该
用 Global VRS。但当前这样有个好效果——FUT 靠履历拿到 Stage 3 资格，却因为当前
Entry 不够被排在层内靠后，进来要自己证明配不配得上这个位置。先不改。

**明确不做**：把真实队也改成用 Entry 模拟 VRS。那等于把现实履历彻底降级成
装饰字段，而且 AI 当前四维还在建设期，一次数据变动就能让现实第 4 的队掉进
Stage 1，「真实 Major 外壳」就没意义了。

### 散场那页改用引擎的尺子

`draft.score()` 曾经是 `火力 40% + 指挥 20% + 经验 20% + 稳定 20% + 默契`，和 v1
的 Entry 同源。问题不在于算得对不对，而在于**比赛不这么算**——v0.3 §4.1 之后
L/E/S 的静态权重已经拿掉了，决定一张图胜负的是纯火力 + IGL 战术执行 + 磨合。

后果是散场那页会告诉你「这一手选 A 比选 B 好 2 分」，而引擎根本不按这个数打。
**后悔值和实际后果是脱节的**，而后悔值正是 Blind Draft 的收尾体验。

现在 `score()` 整段直接问引擎：`Team.entry()`（含 Carry 权重和无狙 −4）加
`tactical()`，**不留任何一份公式的副本**。「单场发挥 X~Y」那条也换成引擎的
σ（§6 的分布不对称，所以给两个数而不是一个 ±）。

一并收掉两处：

- **`draft.score()` 不能删。** 一开始以为它没用了，查下来它是散场页的骨架：
  逐张算「当时最优是谁、差多少」，以及「你的阵容在全部可能组合里排第几」。
  删掉等于删掉后悔机制。所以是**换算法**，不是删。
- **网页那份 JS 副本。** 选人页要在浏览器里当场给出「这是支什么队」，来回请求
  服务端不现实，所以模板里有一份 JS 实现。以前 `.35/.25/.40` 和
  无狙 −4 是两边各抄一遍的。现在系数全部由 `export_web` 从 `blinddraft.engine`
  注入（`D.engine`），`tests/test_web_matches_python.py` 再用 node 把两边跑同一
  批阵容对齐到小数点后 9 位（没装 node 就跳过）。

  模板已由 `draft_web.html` 换成 `Blind_Draft.html`（四屏：选人 / 揭晓 / Run /
  结局）。新页面不再枚举替代阵容，所以 JS 侧只留 Entry 那一条式子；对齐测试
  钉的也从 `score()` 改成 `entryOf()`——揭晓页的「纸面火力」必须和 `/api/run`
  返回的 `entry` 是同一个数。

### 顺带修掉：玩家的默契从来没进过比赛

对齐两把尺子的时候露出来的：`player_run` 把玩家队的磨合度**写死成 0.0**，而
AI 一律吃满 `cohesion_cap`。也就是说 `chemistry()` 算出来的那些东西——真队友
重聚、同国、同代、两个指挥抢话——在选人页上写得清清楚楚（REUNION 标签、
「可以去追」提示都在推你去凑），**却完全没有进比赛**。追一对真队友和不追，
打出来一模一样。

v1 是算的（`Entry("YOUR TEAM", roster, entry_rating(...))`），v2 接管 `/play`
时漏了。现在 `player_cohesion()` 按 §5.2 的口径算 `min(裸默契, cap)`，
`/play` 和 `--demo` 共用它。

还有一处同源的错：`score()` 用的是**裸默契**，引擎用的是**封顶后**的。随机
阵容里只有 1.4% 的裸默契会超过 4.0，所以平时看不出来——但玩家一旦真去凑
REUNION，裸默契能到 9.0，页面按 9 显示、引擎按 4 打，又是两把尺子。两边现在
都取封顶值，页面在被封顶时会把裸默契一起写出来。测试里钉死了三支高默契阵容，
不靠随机抽样碰运气。

### 回归闸门

`tests/test_star_visibility.py`，19 项，分两组（v1 那组随 v1 一起删了，它的
断言翻译成 v2 口径并进了下面第一组）：

- **`MatchV2Tests`（12 项）** 冻结的 Stability 分位数、§8.3 的三个压力例子、
  Leadership 的胜率目标区间（锁的是**胜率**不是分数，所以 MAP_SCALE 一变就会
  响）、Map Residual 不许碰 Player Story、BO3 更稳、Entry 里没有 L/E/S，
  外加从 v1 翻译过来的五条：Carry 权重由卡面定死（打乱 roster 顺序权重必须
  跟着人走）、逐项归因加得回 delta（v2 是 `form + choke + capped`）、输的一方
  也能拿 MVP、爆种和崩盘都归低稳定的人、强度只有 `entry() + tactical` 这一个
  来源。
- **`MajorShellTests`（7 项）** 区域名额分层是 8/8/16 且**不许退化成按 Entry
  切**、玩家插队逐级级联且层级人数守恒、比全场都弱就 Failed to qualify、整届
  每支队都打到 3 胜或 3 负、晋级者带进下一层的是新实例（否则上一层战绩会被
  reset 擦掉，曾经真的出现过「Stage 1 晋级 MIBR(1-3)」）、四档压力、整届结果
  可序列化。

另有两个文件：

- `tests/test_player_run.py`（7 项，原名 `test_match_quick.py`）盯 `/api/run`
  这条 HTTP 线和**那把尺子**：返回值可序列化、`build_run` 必须逐字段等于
  `player_run`（后台不许自己再算一遍比赛）、坏阵容在进引擎前就被拒、散场页的
  总分必须精确等于 `entry() + tactical`、改 L/E/S 不许动总分、磨合度封顶在
  两侧一致、默契必须真的进比赛。
- `tests/test_web_matches_python.py`（2 项，需要 node，没装就跳过）把网页那份
  JS 算分和 Python 跑同一批阵容对齐到小数点后 9 位，并禁止 JS 里再出现写死的
  引擎系数。

任何 Match Engine 改动都要先过它。

### 回合引擎：已有设计稿，明确不接

**[../future/回合引擎_v0.1.md](../future/回合引擎_v0.1.md)** 写了怎么把一张图的黑箱结果展开成回合
过程：实时比分、Kill Feed、K/D/A、ADR、KAST、Match Rating、残局。它自己把状态
标成 **Future Design / 暂不接入正式流程**，这里照抄——M2 的闭环还没被真人试玩
验收，不该先去做观赛层。

记两条它对当前代码的约束，免得以后接的时候踩：

- **迁移必须分阶段**（§22）。第一版不许一上来删 Map Residual：先 R0 只做展示，
  再 R1 影子模拟（同时跑、不影响正式结果、比对胜率曲线和 Star Visibility），
  R2 才让 Round Engine 参与判胜并把 MAP_SCALE 从 6 逐步降下来。
- **两层随机不能合并**（§21）。「谁今天状态好」和「这个关键局发生了什么」必须
  是两个随机源，否则又回到 v1 那种变量语义混乱。

它列的回归测试里有两条我们已经有了：§25.1 的胜率曲线（`--tune`）和 §25.2 的
Star Visibility（`test_star_visibility.py`）。真接的时候这两条直接复用，Round
Engine 不许把明星贡献重新平均掉。

### v1 已退役（`blinddraft/match.py` 已删除）

`/play` 切到 v2 之后，v1 只剩自己的 CLI 和两个测试文件在用，生产代码里一处
import 都没有了。留着一份**算法不同、名字相同**的实现（`run_stage`、
`pair_group`、`run_major`、`insert_player` 在两边都有，相似度 0.8~0.94 但
Stage 规则相反）只会让人挑错的那份看，所以整个删掉。

四个还有用的入口搬到了 v2，口径换成 v2 的：

| v1 入口 | 现在 |
|---|---|
| `--roster "a,b,c" --label X` | `blinddraft.engine --major/--demo` 直接吃这个 spec（`roster_cards`，认昵称也认 page） |
| `--duel HIGH LOW` | `blinddraft.engine --duel`（探针队的 `entry()` 精确等于给的目标值） |
| `--stats` | `blinddraft.engine --stats`：Q1 改成「进 Playoffs 的概率」并把 VRS Stage 印在旁边，两把尺子的错位在表上看得见；Q2 的实力差改用纯火力 Entry |
| `--selftest` 的两条不变量 | Swiss 记账在 `MajorShellTests`；「不 Roll 时强度 == Entry」翻译成 `entry() + tactical` 进了 `MatchV2Tests` |

**没搬、也不打算搬的**：`--quick-run`（`--lab` 的探针队更干净）、v1 `--lab` 的
Q4 经验对照（`--lab` 第 4 项和 `test_pressure_reshapes_the_same_roll_not_a_new_one`
已经覆盖）。**Q3 的那半条漏了**：v1 用 `_stage_spread` 量「高稳定该带来更窄的
战绩分布，而不是更高胜率」——把两支基准强度相同的队塞进同一个 Stage 打 6000 次
比 3-0 / 0-3 的比例。v2 只在单图层面（MVP 率、分位数）覆盖了它，**Stage 层面
没有**。要重新做的话是一个 `--spread`。

顺带收掉的两处：

- **v2 内部有两个赛场构造器**。`field_teams` 走 `major.make_field`（听
  `field_source`），`major_field` 走区域 VRS 名额；`--lab / --demo` 用前者，
  `--major / --field / --audit / /play` 用后者。今天两者输出恰好一致，所以
  一直没人发现，但把 `field_source` 翻成 `major_pool` 就会**静默**分叉——
  验收在历史阵容上跑，玩家面对的是另一批队。已删掉 `field_teams`，只剩一个。
- **`major.py` 里那套 v1 的插队/分层**（`Shove` / `insert_player` / `stage_of` /
  `stage_seeds` / `round1`）已删。它按 Entry 全场排名切 8/16/32，和 v2 的区域
  VRS 名额对 32 支里的 13 支给出不同答案，而 `python -m blinddraft.major --seed 1`
  一直在按那条已退役的规则画 Stage 分割线。现在 major.py 只管**赛场从哪来**，
  怎么打全在 v2；它的赛场列表把真实的 VRS Stage 当一列印出来。

### 比赛引擎拆成 `blinddraft/engine/`

v1 删掉之后，剩下的那一个引擎变成了一个 **1492 行的 `proto_match_v2.py`**：
系数、随机数、队伍、赛制、玩家那一届的装配、命令行打印、验收台、两张审计表，
全在同一个文件里。于是「改一行输出格式」和「改一条胜率系数」打开的是同一份
文件，而且改动的 diff 落在哪一层要靠读上下文猜。

按「一个文件一件事」拆成一个包，**行为一字未改**——拆完拿旧文件和新包逐项
对拍：`player_run` 三支固定阵容 × 5 个种子共 15 次，输出 JSON 完全相同；
`--lab / --compare / --tune / --stats / --duel / --field / --audit /
--audit-cards / --demo` 九个入口的 stdout 逐字节相同。

| 文件 | 管什么 |
|---|---|
| `params.py` | 全部系数，以及由系数直接导出的曲线。**参数只有这一处** |
| `roll.py` | 一个人一张图的那一个随机数（§6 / §8） |
| `team.py` | `Team`：静态 Entry + 五个 Roll 聚合成队伍强度（§4/§5/§9） |
| `play.py` | 一张图 / 一场 BO：Margin 与 Map Residual（§13） |
| `tournament.py` | 赛制外壳：赛场、三段 Swiss、玩家插队（§1~§2） |
| `roster.py` | 引擎与卡库之间唯一的接口；玩家磨合度也在这 |
| `probes.py` | 形状受控的假队伍，只给验收和调参用 |
| `run.py` | 玩家的一整届 -> 一个 JSON（网页和命令行共用） |
| `report.py` | 命令行打印层，只排版不算数 |
| `lab.py` | 验收台与调参台（`--lab / --tune / --duel / --stats`） |
| `audit.py` | 两张只读审计表（`--audit / --audit-cards`） |
| `__main__.py` | `python -m blinddraft.engine`，只解析参数和分发 |

三件顺手定下的规矩：

- **调用方一律 `from blinddraft import engine as V2`**，`__init__.py` 只做转发、
  没有任何实现。以后再切文件不波及调用方。
- **会被扫描或改写的量必须写成 `PA.MAP_SCALE`**（`from . import params as PA`），
  不许 `from .params import MAP_SCALE`。后者绑的是当时那个值，`lab.tune()` 改了
  `params.SIGMA_SCALE` 它不跟着变——扫描表里五行数字一模一样，而且不报错。
  只有函数（`tactical` / `soft_cap` / `sigma_up`…）可以按名字导入。
- **模块名不复用退役的名字。** 一张图/一场那层叫 `play.py` 不叫 `match.py`，
  免得和刚删掉的 v1 `blinddraft/match.py` 在搜索结果里混在一起。

`--quick-run` 之类的旧入口没有回来；`proto_match_v2` 这个名字也**没有留兼容
别名**——这个仓库刚为「两个东西同名」付过一次代价，不再留第二个。
