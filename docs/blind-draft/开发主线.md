# Blind Draft 当前开发主线

> 生效时间：2026-09-02。若历史设计稿、实验记录与本页冲突，以本页决定“下一步做什么”；
> 历史文档仍负责解释规则从哪里来，不删改当时结论。

## 产品目标

当前目标不是继续把 648 张选手卡逐张修到“没有争议”，而是完成这一条玩家可感知的闭环：

```text
不完整信息下签下 5 人
→ 看见阵容的优势、缺陷和构筑方向
→ 让这支队经历 BO1 / BO3 / 高压生死局
→ 从比赛事件看见 Firepower / Stability / Experience / Leadership 做功
→ Reveal 身份、完整卡面和这次选择造成的后果
```

判断一个任务是否优先，只问一句：

> 它能否让玩家更清楚地感到“我刚才选的五个人，导致了后来发生的事”？

不能回答这句话的整库精修、页面扩建和远期系统，默认不进入当前里程碑。

## 三个世界必须分开

| 世界 | 问题 | 权威来源 |
|---|---|---|
| 玩家卡 | 这个人职业生涯代表版本是什么样 | `cards.generate()` → `draft_cards.json` |
| AI 当前卡 | 这个人在当前阵容里是什么样 | 玩家卡先验 + `team_snapshot.json` + `5e_player_stats.json` |
| 单场表现 | 他今天这一张图打成什么样 | `match.py` 的 Form Roll / 压力机制 |

`draft_cards.json` 可以作为 AI 当前卡的**生涯先验**，不能整卡复制成当前真值：

- Firepower：当前 5E 证据优先；样本不足时向生涯先验收缩；无证据才回退。
- Leadership：按当前队内位置解释，证据仍来自生涯 IGL 履历。
- Experience：职业经历不会随当前状态消失，主要继承玩家卡。
- Stability：现有聚合 KAST 不是逐图方差；取得逐图数据前只作低置信先验。
- Grade：只表示 Career Evidence，不参与 AI 当前实力或“捡漏”判定。

卡库外新人是真人，不再用匿名 G1 占位替换。他们可以拥有 AI 专属的当前四维，
但不会因此进入玩家抽卡库；每个推导值必须带来源和置信度。

## 执行顺序

### M0 — 数据底座收口（已完成）

1. 同一份源码和人工层必须稳定生成同一份 `draft_cards.json`。
2. CI/测试直接比较实时生成结果与已发布文件，禁止“后台显示一套、比赛读取另一套”。
3. 清理待定角色；新增人工结论必须写理由。

完成标准：卡库待发布差异为 0，待定位置为 0，生成器幂等测试通过。

### M1 — 统一 AI 当前卡（第一版已接通，待真人审计）

1. 建一个逐维 current projection，不再把“年龄衰减后的生涯卡”当完整当前卡。
2. AI 页面、Major 入场和 Match 只消费这一份生成结果。
3. 当前阵容和位置只认 `team_snapshot.json`；不再从卡上的 `team` 拼阵容。
4. 卡库外但有当前证据的人生成透明的低置信先验，不造虚构球员。

完成标准：32 个正赛席位均有五名真实首发和可计算四维；页面与 Match 的阵容、位置、
四维逐项相同；每个与玩家卡不同的值都有来源说明。

### M2 — 极简 Run（网页第一版已接通）

先做一条短而完整的体验，不先扩完整赛事 UI：

1. 一场 BO1；
2. 一场 BO3；
3. 一场高压生死局；
4. 每图展示赛前预期、实际队伍强度、MVP/Life Game、关键失常或压力兜底；
5. 结束时 Reveal 完整卡面和阵容选择的后果。

完成标准：真人试玩能用比赛事件解释至少一次选人后悔或惊喜，而不是只看到随机比分。

当前第一版可直接运行：

```powershell
python -m blinddraft.match --seed 50296 --quick-run
python -m blinddraft.match --duel 80 50 --duel-runs 20000
```

也可启动本地后台后打开 `/play`：选满五人点击“开始 Run”，页面通过 `/api/run`
提交五个 page id；Python 按 Projected Seed 跑真实三段 Swiss 并返回玩家路径 JSON。
前端只渲染，不复制 Match 公式。命令行 `--quick-run` 仍保留为固定三场、同强度对手
的控制变量测试台，不作为玩家正式 Run。

命令行 `--quick-run` 的三场仍调用正式 `play_match()`：普通 BO1、BO3、2-2
高压 BO3；对手从本届真实队中取 Entry 最接近的三支。它只用来控制变量地测试
四维是否有存在感，网页玩家 Run 不使用这套匹配。

第一组胜率锚（同样四维形状，只差 Entry 80 / 50，20 万次复核）：BO1 强队约
90.8%，BO3 约 97.6%。这意味着大差距不是必胜，但 BO3 会显著压低爆冷。网页
Run 走 Swiss 的真实首轮种子与同战绩配对，不会连续强制匹配同 Entry 对手。

### M3 — 用试玩校准

只有在闭环可玩后，才回头处理：

- Stability 的赛事层偏差；
- Leadership / Experience / Stability 的逐维 audit；
- Ability Value、Market、Bargain / Overpay；
- 完整 Major、Rogue Buff、地图池和 Pick/Ban。

## 当前明确不做

- 不逐张人工维护第二份 AI 卡 JSON；AI 卡必须是生成物。
- 不因为 AI 当前数据好看就修改玩家卡的 Career Grade。
- 不用 KAST 直接生成 Stability。
- 不为了贴合 HLTV/VRS 排名反向篡改单个选手四维；队伍级异常走有理由的 `adjust`。
- 不在极简 Run 验证前扩淘汰赛、Buff、地图池或完整赛事 UI。
- 不以“整库相关性更高”替代玩家可解释性。

## 每次提交前的检查

- 改的是玩家卡、AI 当前卡，还是单场表现？只能属于其中一层。
- 是否引入了新的人工权威源？如果是，停止。
- 生成物能否从源码和人工层完整重建？
- 页面展示和 Match 实际读取的是不是同一份值？
- 这个改动会通过什么比赛事件被玩家感知？
