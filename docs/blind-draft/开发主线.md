## 产品目标

当前目标不是继续把 648 张选手卡逐张修到“没有争议”，而是完成这一条玩家可感知的闭环：

```text
不完整信息下签下 5 人
→ 看见阵容的优势、缺陷和构筑方向
→ 让这支队经历 BO1 / BO3 / 高压生死局
→ 从比赛事件看见 Firepower / Stability / Experience / Leadership 做功
→ Reveal 身份、完整卡面和这次选择造成的后果
```

判断一个任务是否优先，只问一句：

> 它能否让玩家更清楚地感到“我刚才选的五个人，导致了后来发生的事”？

不能回答这句话的整库精修、页面扩建和远期系统，默认不进入当前里程碑。

## 现在是什么样

**「v1 / v2」从头到尾只是比赛数值层的版本号，不是整个项目的版本号。** 四层里
只有一层经历了 v1 → v2，别的层各有各的来路：

| 层 | 现在归谁管 | 权威设计稿 | 和 v1/v2 的关系 |
|---|---|---|---|
| 玩家卡（生涯卡，648 张） | `blinddraft/cards.py`（v7） | `卡牌与落地记录.md` ← `archive/玩法蓝图_v0.2.md` + `archive/四维重构_v0.1.md` | **无关**，从没被替换过 |
| AI 当前卡 | `blinddraft/ai_teams.py` | `数据快照.md` | **无关**，另一条线（5E 证据接管当前火力） |
| 比赛数值层 | `blinddraft/engine/` | `比赛引擎_v0.3.md` | **这一层才是 v1 → v2，已彻底换掉** |
| 赛制外壳（32 队三段瑞士轮） | `blinddraft/engine/tournament.py` | `archive/比赛引擎_v0.1.md` §1~§2 | **是旧设计，而且故意保留** |

最后一行最容易被误会：32 队怎么来、三段 Swiss 怎么打、Buchholz 怎么算、
BO1/BO3 怎么定，全部出自 v0.1 那份稿子，v0.3 **没有替换它**——那一层是赛制不是
数值。v2 只是重新实现了一遍（好让 v1 能干净地删掉），并改了一处：Stage 归属听
区域 VRS 名额，不再听 Entry 排名。所以 `archive/比赛引擎_v0.1.md` 前三节至今
是赛事外壳的唯一出处。

**比赛引擎只有一份实现，`blinddraft/engine/`。** v1（`blinddraft/match.py`）已
删除，唯一残留是 `V1_WIN_SCALE = 13.0` 一个常量，只给 `--compare` 画历史对照
曲线，引擎里没有任何地方读它。

```powershell
uvicorn bdserver.main:app --host 127.0.0.1 --port 8621   # 然后开 /play
python -m blinddraft.engine --lab            # 六项验收
python -m blinddraft.engine --tune           # MAP_SCALE 扫描
python -m blinddraft.engine --duel 80 70     # 两个 Entry 之间的胜率锚（实测）
python -m blinddraft.engine --stats --runs 200        # 整届分布
python -m blinddraft.engine --field                   # 32 席怎么来的
python -m blinddraft.engine --major "donk carry"      # 跑完整一届
python -m blinddraft.engine --demo "donk carry"       # 打一场，看逐人账本
python -m blinddraft.engine --audit                   # VRS × Entry 偏差审计
python -m blinddraft.engine --audit-cards             # 谁的四维是猜的
```

### 网页有两个，玩的是同一份 Python

| 入口 | 是什么 | 选人 | 比赛 |
|---|---|---|---|
| `/play` | 老的自包含单页（`templates/Blind_Draft.html` + `bdtools.export_web`） | **JS 自己发牌**，常量由 export_web 注入 | `/api/run` |
| `/broadcast` | 转播外壳（`web/`，React，`npm run build` 出单文件） | `/api/draft` | `/api/run` |

`/broadcast` 是**纯外壳**：所有玩法、数值、随机数走后端，它拿到什么就画什么。
原来那 578 行独立引擎 `src/game/engine.ts` 和 78 张虚构卡 `src/data/players.ts`
已经删掉，`test_broadcast_shell.py` 盯着它们别回来、也盯着引擎系数不许抄进 TS。

新增的 `/api/draft`（`bdserver/draft.py`）把**选人**也收进了 Python：一局 =
`seed` + 一串动作，无会话、可重放，同一个 seed 和命令行 `--seed` 是同一局，
板面只下发球探区间和线索、不下发真值（`page` / 昵称 / 档位 / 四维一概不给）。

**老 `/play` 那份 JS `draw()` 现在是仅存的第二份发牌实现**：规则和
`Dealer._draw` 相同，随机数流不同，所以同一个 seed 在两边不是同一局，而
`test_web_matches_python.py` 只对齐了 Entry，没有任何东西盯着这个差。要么把
`/play` 也切到 `/api/draft`，要么等 `/broadcast` 覆盖完它的能力后退役它。

后端没有的功能（Rogue Buff 商店、淘汰赛、夺冠、后悔值复盘）在外壳里用
`<NotImplemented>` **明写「未实现」并说明为什么**，不用前端逻辑补，也不把入口
藏掉——藏起来会让人以为做完了。逐回合播报和 K/D 是**表演层**
（`src/game/playByPlay.ts`）：比分收敛到引擎给的那一图结果，不参与任何判定，
删掉那个文件比赛结果一分不变；比赛屏上它和引擎的逐人账本并排摆着。


## 三个世界必须分开

| 世界 | 问题 | 权威来源 |
|---|---|---|
| 玩家卡 | 这个人职业生涯代表版本是什么样 | `cards.generate()` → `draft_cards.json` |
| AI 当前卡 | 这个人在当前阵容里是什么样 | 玩家卡先验 + `team_snapshot.json` + `5e_player_stats.json` |
| 单场表现 | 他今天这一张图打成什么样 | `blinddraft/engine/` 的 Player Roll / 压力机制 |

`draft_cards.json` 可以作为 AI 当前卡的**生涯先验**，不能整卡复制成当前真值：

- Firepower：当前 5E 证据优先；样本不足时向生涯先验收缩；无证据才回退。
- Leadership：按当前队内位置解释，证据仍来自生涯 IGL 履历。
- Experience：职业经历不会随当前状态消失，主要继承玩家卡。
- Stability：**没有任何当前证据能碰这一维**，只有生涯先验一个来源。聚合 KAST
  不是逐图方差，不许用它生成；出场量是 Evidence Confidence，也不折算成稳定值。
- Grade：只表示 Career Evidence，不参与 AI 当前实力或“捡漏”判定。

卡库外新人是真人，不再用匿名 G1 占位替换。他们可以拥有 AI 专属的当前四维，
但不会因此进入玩家抽卡库；每个推导值必须带来源和置信度。

## 现在守着的规矩

下面每条都有测试或工具盯着，改动前先看它。数字是怎么量出来的在
[archive/引擎重构记录_v1到v2.md](archive/引擎重构记录_v1到v2.md)。

**Entry 只有一个定义。** `engine.entry_of(roster, chem, adjust)`＝纯火力
（Carry 权重 .35/.25/.40）+ 磨合 + 结构修正（无狙 −4），量纲 ≈80。v1 那个
「火力 40% + L/E/S 各 20%」（≈65）已删除，不是改名。两者对同一批队最多差 15
个名次，页面显示一套、比赛读另一套一定会把人绕晕。`OneEntryDefinitionTests` 盯着。

**页面显示的必须就是比赛读的。** 选人页的纸面火力、散场页的后悔值、`/ai` 的
Entry、`/play` 里上场的，是同一个函数算的。网页那份 JS 的系数由 `export_web`
从 `blinddraft.engine` 注入（`D.engine`），不许在 JS 里写死；
`test_web_matches_python.py` 用 node 把两边对齐到小数点后 9 位。

**胜率只能 Monte Carlo 实测，不能从系数上算。** `MAP_SCALE` 只控制 Map
Residual 那一层，整条曲线是 Player 波动和 Residual 的卷积，等效 scale 随分差
从 7.1 漂到 6.4——连 logistic 形状都不是。动过任何队伍层 modifier 之后，
`--duel` / `--tune` 那几张表要重跑。

**宏观爆冷只许调 MAP_SCALE（当前 6.0）。** §6.3 已冻结 Stability 分布，放大
个人波动能把爆冷拉回来，代价是 F80/S50 单图能打 11~130，Player Story 就毁了。
队内相关性也不行（只对齐不放大）。

**`map_count` 是 Evidence Confidence，不是 Stability。** 出场量只决定火力那一维
信不信当前证据（硬门槛 10 图，10~79 图向生涯先验收缩），**不折算成稳定值**。
试过扣稳定值，实测是对同一批人罚两次、把爆冷压没了（实力差 10~15 时 BO1 强队
胜率 86.6% → 91.9%），已撤回。一支队打得少是我们的认知问题，不该变成它在比赛
里的惩罚。`EvidenceConfidenceTests` 盯着这条别被「听起来有道理」地加回来。

**引擎参数只有 `engine/params.py` 一处。** 会被扫描或改写的量（`MAP_SCALE` /
`SIGMA_SCALE` / `TEAM_RHO`）必须写成 `PA.MAP_SCALE`——`from .params import
SIGMA_SCALE` 绑的是当时那个值，`lab.tune()` 改了它不跟着变，扫描表里五行数字
会一模一样**而且不报错**。只有函数可以按名字导入。

**模块名不复用退役的名字。** 一张图/一场那层叫 `play.py` 不叫 `match.py`。
`proto_match_v2` 也没有留兼容别名。

### 回归闸门

任何比赛数值层的改动都要先过这四个文件（共 54 项）：

| 文件 | 项 | 盯着什么 |
|---|---:|---|
| `test_star_visibility.py` | 19 | `MatchV2Tests` 12 项：冻结的 Stability 分位数、§8.3 的三个压力例子、Leadership 的**胜率**目标区间（MAP_SCALE 一变就响）、Map Residual 不许碰 Player Story、Carry 权重由卡面定死、逐项归因加得回 delta、强度只有 `entry() + tactical` 一个来源。`MajorShellTests` 7 项：分层 8/8/16 不许退化成按 Entry 切、插队逐级级联且名额守恒、晋级者是新实例、四档压力 |
| `test_ai_view.py` | 26 | AI 页与 Match 共用同一份阵容和四维；Entry 唯一定义；出场量不折算成稳定值 |
| `test_player_run.py` | 7 | `/api/run` 逐字段等于 `player_run`；散场页总分精确等于 `entry() + tactical`；磨合度封顶两侧一致 |
| `test_web_matches_python.py` | 2 | JS 与 Python 同阵容同结果（需 node，没装就跳过）；JS 里不许出现写死的引擎系数 |


## 执行顺序

### M0 — 数据底座收口（已完成）

1. 同一份源码和人工层必须稳定生成同一份 `draft_cards.json`。
2. CI/测试直接比较实时生成结果与已发布文件，禁止“后台显示一套、比赛读取另一套”。
3. 清理待定角色；新增人工结论必须写理由。

完成标准：卡库待发布差异为 0，待定位置为 0，生成器幂等测试通过。

### M1 — 统一 AI 当前卡（第一版已接通，待真人审计）

1. 建一个逐维 current projection，不再把“年龄衰减后的生涯卡”当完整当前卡。
2. AI 页面、Major 入场和 Match 只消费这一份生成结果。
3. 当前阵容和位置只认 `team_snapshot.json`；不再从卡上的 `team` 拼阵容。
4. 卡库外但有当前证据的人生成透明的低置信先验，不造虚构球员。

完成标准：32 个正赛席位均有五名真实首发和可计算四维；页面与 Match 的阵容、位置、
四维逐项相同；每个与玩家卡不同的值都有来源说明。

### M2 — 极简 Run（网页第一版已接通）

先做一条短而完整的体验，不先扩完整赛事 UI：

1. 一场 BO1；
2. 一场 BO3；
3. 一场高压生死局；
4. 每图展示赛前预期、实际队伍强度、MVP/Life Game、关键失常或压力兜底；
5. 结束时 Reveal 完整卡面和阵容选择的后果。

完成标准：真人试玩能用比赛事件解释至少一次选人后悔或惊喜，而不是只看到随机比分。

玩家正式入口是本地后台的 `/play`：选满五人点「开始 Run」，页面把五个 page id
提交到 `/api/run`，Python 按 Projected Seed 跑真实三段 Swiss 并返回玩家路径
JSON。前端只渲染，不复制任何 Match 公式。

```powershell
uvicorn bdserver.main:app --host 127.0.0.1 --port 8621   # 然后开 /play
python -m blinddraft.engine --lab                # 四维有没有存在感
python -m blinddraft.engine --duel 80 70         # 胜率锚（实测）
python -m blinddraft.engine --stats --runs 200   # 整届分布
```

**胜率锚必须实测，不能从系数上算**（§13.3）。v2 口径（Entry 是纯火力，两队只差
Entry、四维形状相同，各 2 万次）：

| Entry 差 | BO1 强队胜率 | BO3 强队胜率 |
|---:|---:|---:|
| 5（80 vs 75） | 68.0% | 75.6% |
| 10（80 vs 70） | 81.9% | 91.3% |
| 30（80 vs 50） | 99.2% | 100.0% |

大差距不是必胜，但 BO3 会显著压低爆冷。**旧文档里的「BO1 90.8% / BO3 97.6%」是
v1 在 Entry 80/50 上的数**，v1 的 Entry 含 L/E/S、量纲在 65 上下，和这张表不可比。
动过 MAP_SCALE / SIGMA_SCALE / 任何队伍层 modifier 之后，这张表要重跑。

M2 跑通后的第一次真人试玩暴露了比赛数值层的结构性问题，于是有了 v1 → v2 那轮
重构。**它已经做完了**，过程见
[archive/引擎重构记录_v1到v2.md](archive/引擎重构记录_v1到v2.md)。

### M3 — 用试玩校准

只有在闭环可玩后，才回头处理：

- Ability Value、Market、Bargain / Overpay；
- 完整 Major、Rogue Buff、地图池和 Pick/Ban；
- Leadership / Experience / Stability 的逐维 audit（**卡面那一侧**——四维在
  比赛里怎么做功已经由 v1 → v2 那轮重构接管，这里剩下的是「这个人的 S 该不该
  是 46」这类取值问题）。

原先列在这里的「Stability 的赛事层偏差」已经不属于 M3：它是比赛数值层的结构
问题，那轮重构已经处理掉了。

## 下一步

判断优先级只问一句：它能否让玩家更清楚地感到「我刚才选的五个人，导致了后来
发生的事」。按这个排：

1. **正常玩几把 `/play`。** M2 的闭环已经接通但还没被真人试玩验收过，M3 的
   全部校准都等这一步的信号。在这之前不扩系统。
2. **卡库外真人的 Leadership / Experience 没有数据源。** 正赛 26 人（16%）这
   两维仍是角色模板常量。火力那一维已经有救（5E 证据 + 10 图门槛），这两维
   连从哪来都还没定。`--audit-cards` 最后一张表专门列它们。
3. **`--spread`：Stage 层的稳定性分布对照没了。** v1 用 `_stage_spread` 量
   「高稳定该带来更窄的战绩分布，而不是更高胜率」——两支基准强度相同的队塞进
   同一个 Stage 打 6000 次，比 3-0 / 0-3 的比例。v2 只在单图层面覆盖了它。
4. **BIG 那类 5E 覆盖不足的队要重抓数据。**

### 玩家的 Stage 判据仍是临时规则

现在是「Entry 全场排名 → 8/16/32，然后名额守恒逐级级联」。它明显好过最初的
「逐层挤」（两把尺子秩相关只有 0.63，层间 Entry 重叠严重，一支 62 分的队能挤进
Stage 2 却比 Stage 1 半数队都弱），但架构上仍是两套判据并存：真实队走 VRS，
玩家走 Entry。

长期方向是引入第三个概念 **Projected / Synthetic VRS**：

```text
真实队：Current VRS + 由 Entry 预测的有界变动 -> Projected VRS -> 区域 cutoff -> Stage
玩家：  Entry percentile -> Synthetic VRS      -> 区域 cutoff -> Stage
```

叙事变成「假定你的梦之队在邀请截止前已经打了一段未展开模拟的资格竞争」，比
「因为你 Entry 全场第 12，所以判你 Stage 2」自然得多。

**现在不做**，因为第一版的底层仍然是 Entry percentile，做出来数值上和现在完全
等价、只是换了个名字，反而让人以为 Projected VRS 已经实现了。等真的要做真实队
的 VRS 变动预测时，两件事一起做才有意义。

**明确不做**：把真实队也改成用 Entry 模拟 VRS。那等于把现实履历降级成装饰
字段，一次数据变动就能让现实第 4 的队掉进 Stage 1，「真实 Major 外壳」就没
意义了。

### 还没接的

§11 Trait / Rogue Buff、§10 Chemistry cap 在新标尺上重扫、§2.4 Playoffs。
回合引擎有设计稿但明确不接，理由和它对当前代码的两条约束见
[future/README.md](future/README.md)。


## 当前明确不做

- 不逐张人工维护第二份 AI 卡 JSON；AI 卡必须是生成物。
- 不因为 AI 当前数据好看就修改玩家卡的 Career Grade。
- 不用 KAST 直接生成 Stability。
- 不为了贴合 HLTV/VRS 排名反向篡改单个选手四维；队伍级异常走有理由的 `adjust`。
- 不在极简 Run 验证前扩淘汰赛、Buff、地图池或完整赛事 UI。
- 不以“整库相关性更高”替代玩家可解释性。

## 每次提交前的检查

- 改的是玩家卡、AI 当前卡，还是单场表现？只能属于其中一层。
- 是否引入了新的人工权威源？如果是，停止。
- 生成物能否从源码和人工层完整重建？
- 页面展示和 Match 实际读取的是不是同一份值？
- 这个改动会通过什么比赛事件被玩家感知？
