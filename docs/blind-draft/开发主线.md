# Blind Draft 当前开发主线

> 生效时间：2026-09-02。若历史设计稿、实验记录与本页冲突，以本页决定“下一步做什么”；
> 历史文档仍负责解释规则从哪里来，不删改当时结论。

## 产品目标

当前目标不是继续把 648 张选手卡逐张修到“没有争议”，而是完成这一条玩家可感知的闭环：

```text
不完整信息下签下 5 人
→ 看见阵容的优势、缺陷和构筑方向
→ 让这支队经历 BO1 / BO3 / 高压生死局
→ 从比赛事件看见 Firepower / Stability / Experience / Leadership 做功
→ Reveal 身份、完整卡面和这次选择造成的后果
```

判断一个任务是否优先，只问一句：

> 它能否让玩家更清楚地感到“我刚才选的五个人，导致了后来发生的事”？

不能回答这句话的整库精修、页面扩建和远期系统，默认不进入当前里程碑。

## 三个世界必须分开

| 世界 | 问题 | 权威来源 |
|---|---|---|
| 玩家卡 | 这个人职业生涯代表版本是什么样 | `cards.generate()` → `draft_cards.json` |
| AI 当前卡 | 这个人在当前阵容里是什么样 | 玩家卡先验 + `team_snapshot.json` + `5e_player_stats.json` |
| 单场表现 | 他今天这一张图打成什么样 | `match.py` 的 Form Roll / 压力机制 |

`draft_cards.json` 可以作为 AI 当前卡的**生涯先验**，不能整卡复制成当前真值：

- Firepower：当前 5E 证据优先；样本不足时向生涯先验收缩；无证据才回退。
- Leadership：按当前队内位置解释，证据仍来自生涯 IGL 履历。
- Experience：职业经历不会随当前状态消失，主要继承玩家卡。
- Stability：现有聚合 KAST 不是逐图方差；取得逐图数据前只作低置信先验。
- Grade：只表示 Career Evidence，不参与 AI 当前实力或“捡漏”判定。

卡库外新人是真人，不再用匿名 G1 占位替换。他们可以拥有 AI 专属的当前四维，
但不会因此进入玩家抽卡库；每个推导值必须带来源和置信度。

## 执行顺序

### M0 — 数据底座收口（已完成）

1. 同一份源码和人工层必须稳定生成同一份 `draft_cards.json`。
2. CI/测试直接比较实时生成结果与已发布文件，禁止“后台显示一套、比赛读取另一套”。
3. 清理待定角色；新增人工结论必须写理由。

完成标准：卡库待发布差异为 0，待定位置为 0，生成器幂等测试通过。

### M1 — 统一 AI 当前卡（第一版已接通，待真人审计）

1. 建一个逐维 current projection，不再把“年龄衰减后的生涯卡”当完整当前卡。
2. AI 页面、Major 入场和 Match 只消费这一份生成结果。
3. 当前阵容和位置只认 `team_snapshot.json`；不再从卡上的 `team` 拼阵容。
4. 卡库外但有当前证据的人生成透明的低置信先验，不造虚构球员。

完成标准：32 个正赛席位均有五名真实首发和可计算四维；页面与 Match 的阵容、位置、
四维逐项相同；每个与玩家卡不同的值都有来源说明。

### M2 — 极简 Run（网页第一版已接通）

先做一条短而完整的体验，不先扩完整赛事 UI：

1. 一场 BO1；
2. 一场 BO3；
3. 一场高压生死局；
4. 每图展示赛前预期、实际队伍强度、MVP/Life Game、关键失常或压力兜底；
5. 结束时 Reveal 完整卡面和阵容选择的后果。

完成标准：真人试玩能用比赛事件解释至少一次选人后悔或惊喜，而不是只看到随机比分。

玩家正式入口是本地后台的 `/play`：选满五人点「开始 Run」，页面把五个 page id
提交到 `/api/run`，Python 按 Projected Seed 跑真实三段 Swiss 并返回玩家路径
JSON。前端只渲染，不复制任何 Match 公式。

```powershell
uvicorn bdserver.main:app --host 127.0.0.1 --port 8621   # 然后开 /play
python -m blinddraft.match --seed 50296 --quick-run      # 控制变量测试台
python -m blinddraft.match --duel 80 50 --duel-runs 20000
```

`--quick-run` **不是玩家 Run**，是固定三场、对手取 Entry 最接近三支的控制变量
测试台，只用来看四维有没有存在感。网页 Run 走 Swiss 的真实首轮种子与同战绩
配对，不会连续强制匹配同 Entry 对手。

胜率锚（同样四维形状，只差 Entry 80 / 50，20 万次复核）：BO1 强队约 90.8%，
BO3 约 97.6%。大差距不是必胜，但 BO3 会显著压低爆冷。

M2 跑通后的第一次真人试玩直接暴露了比赛数值层的结构性问题，于是有了
[比赛引擎第二轮重构](#比赛引擎第二轮重构进行中)——它是 M3 的前置。

### M3 — 用试玩校准

只有在闭环可玩后，才回头处理：

- Ability Value、Market、Bargain / Overpay；
- 完整 Major、Rogue Buff、地图池和 Pick/Ban；
- Leadership / Experience / Stability 的逐维 audit（**卡面那一侧**——四维在
  比赛里怎么做功已经由下面那轮重构接管，这里剩下的是「这个人的 S 该不该是
  46」这类取值问题）。

原先列在这里的「Stability 的赛事层偏差」已经不属于 M3：它是比赛数值层的结构
问题，归 [比赛引擎第二轮重构](#比赛引擎第二轮重构进行中)。

## 比赛引擎第二轮重构（进行中）

M2 的真人试玩暴露了比赛数值层的结构性问题，权威口径见
**[比赛引擎_v0.3.md](比赛引擎_v0.3.md)**。它是**两条腿并行**：v1 就地修掉
已经确证的错，v2 按新架构另起原型，两套并存直到 v2 被验收。

### v1（`blinddraft/match.py`）已改，正在服役

两处底层错误，改动都已进主引擎并有测试保护：

- **Carry Hierarchy 由卡面定死。** 火力聚合的 `.35 / .25 / .133×3` 以前按
  **当图掷骰结果**重排，等于一次高 Roll 拿两次奖励——自己涨分，还从后排跳到
  主枪位。实测低火力队友能在 12.7% 的图里挤掉 donk。注意这条**几乎不改变
  胜负**（队伍强度均值只差 0.03~0.71 分），它修的是语义。
- **MVP / LIFE GAME / UNDERPERFORM 三个口径拆开。** 旧 `mvp` 只从**赢家一方**
  取 `eff - base` 最大的人，两个后果：输掉的一方永远无人上榜（「核心尽力了、
  队友带不动」讲不出来），而比超常幅度系统性奖励低卡面高波动的人——实测
  spaze(F50) 的 MVP 率 24.3% 反超 donk(F96) 的 19.5%，donk 的 LIFE GAME 率
  恒为 0。现在 MVP 看**最终有效火力、两队合评**，另外两个看偏离。改完 donk
  的 MVP 率 87.3%，spaze 0.0%。

阈值取 `LIFE_GAME_AT = 12`（不是复盘建议的 10）：12 的触发率已接近每四张图
一次，再往下调就变成常态了。

每张图还会给出**十个人的逐人账本**：`delta` 拆成「全队状态 + 个人状态 +
指挥挽回 + 经验挽回 + 软顶」，逐项可加，测试断言无残差。Leadership 在队伍
层面的做功也直接给出（救回的火力按 Carry 权重折算）——它只在负 Roll 时生效，
全队手热的那张图它的贡献精确等于 0。

**v1 没有解决、也不打算在 v1 解决的**：Entry 仍是 `40% 火力 + 20%×3` 的静态
聚合，Stability / Experience 因此被算两遍；`soft_cap` 仍单向压制高火力选手。
这两条属于 v2 的架构问题。

### v2 原型（`blinddraft/proto_match_v2.py`）

实现 v0.3 §15 的 Pipeline。**不碰 `match.py`**——设计稿要求这一版做成独立原型。

```powershell
python -m blinddraft.proto_match_v2 --lab       # 六项验收
python -m blinddraft.proto_match_v2 --tune      # MAP_SCALE 扫描
python -m blinddraft.proto_match_v2 --compare   # 和 v1 的胜率曲线对比
python -m blinddraft.proto_match_v2 --demo "donk carry"
python -m blinddraft.proto_match_v2 --field     # 32 席怎么来的
python -m blinddraft.proto_match_v2 --major "donk carry"   # 跑完整一届
```

**一张图 11 个随机数**：10 个 Player Performance + 1 个 Map Residual。没有
Team Shared Form（§12 退役），没有独立 Choke 骰（§8.3），没有最终 Bernoulli
胜负骰（§13）。四维各做一件事：Firepower 定基线、Stability 定兑现分布、
Experience 只在 Pressure>0 时扭曲同一次 Roll、Leadership 只做 Team Execution。

Entry 是纯火力口径（≈80），**和 v1 的 ≈65 不可直接比较**。

**系数都有出处，没有一个是拍的。** Stability 分布和 Choke 幅度从设计稿举的
例子反推，实测复现：F80/S90 落 75~90、F80/S50 落 63~98；「新人 −7 经验25
生死局 → −11、老将 −7 经验90 → −7.5」。Leadership 则按 §9.2 的新规矩，先定
胜率目标再反推 Strength。

### MAP_SCALE 定 6，但它不是胜率曲线

§13.3 让扫 4/5/6/7，实测（`--tune`）：

| SCALE | +2 | +5 | +10 | +20 | +10 时 BO1 爆冷 |
|---:|---:|---:|---:|---:|---:|
| 4 | 59.2% | 72.7% | 88.7% | 98.8% | 11.3% |
| **6** | **56.7%** | **67.0%** | **81.2%** | **95.9%** | **18.8%** |
| 7 | 55.5% | 65.1% | 78.0% | 93.6% | 22.0% |
| 9 | 54.5% | 62.4% | 72.9% | 88.9% | 27.1% |

6 让四条验收目标同时满足。旧 `WIN_SCALE=13` 确认不迁移——那会让 +10 只剩
68%，选手层重新被宏观随机淹没。

**要订正设计稿 §13.3 的一句话。** 它说 Map Residual 与经典 logistic 胜率
「统计意义上等价」——这只在「双方 Team Performance 是常数」时成立。实际 SA、SB
各含 Player 波动（两队之差 σ≈4.3），Residual 自己 σ≈10.9，最终曲线是两者的
**卷积**：

| 火力差 | 实测（整套） | logistic(gap/6) | 反解等效 scale |
|---:|---:|---:|---:|
| +2 | 57.0% | 58.3% | 7.06 |
| +5 | 67.5% | 69.7% | 6.83 |
| +10 | 81.8% | 84.1% | 6.66 |
| +20 | 95.8% | 96.6% | 6.40 |
| +30 | 99.1% | 99.3% | 6.36 |

等效 scale 不是常数，随分差从 7.1 漂到 6.4——所以整条曲线连 logistic 形状都
不是，谈不上把 MAP_SCALE「换算」成胜率。

> **MAP_SCALE 只控制 Residual 那一层。任何胜率结论都必须靠 Monte Carlo 实测，
> 不能由它解析推导。**

这条对所有队伍层 modifier 都成立：§9.2 那个「先定胜率差再反推 Strength」的
规矩，反推用的换算率（当前 1 分 ≈ 3.5 个百分点）本身就是跑出来的，而且
MAP_SCALE 一动就得重跑。

### v2 六项验收全部达标

`--lab`，6000 次：

| | 结果 |
|---|---|
| 明星 MVP | donk 89.8% / ZywOo 84.9%，spaze 0.0% |
| 低卡 LIFE GAME | spaze 5.5% / Kvem 5.8%，donk 0.2% |
| BO1/BO3 爆冷（火力差 10） | 19.0% → 8.8%，无需任何 BO3 加成 |
| 高压局经验 | 经验 25 −3.1pt，经验 90 +2.6pt |
| 顶级 IGL | gla1ve 级 +4.9pt、无 IGL −8.2pt（目标 4~6 / 6~10，命中） |
| donk carry | 对中游 53.3%，对 Top5 BO1 13~29% / BO3 5~20% |

同火力时高稳定的人 MVP 更多（pronax S77 35.1% > susp S50 29.9%），这正是 §6
「兑现率」想要的形状。

第一版原型曾按更早的复盘把 Residual 那层也删掉，直接比 Team Performance 大小。
实测不行：+5 分就 89.7%、+10 分 99.4%，整届 Major 退化成按 Entry 排序的表格。
`--tune` 下半部分那张「三选二」的表就是这条结论的出处，设计稿 §13.5 采纳了它。

### v2 已接入 Road to Major（VRS 名额 + 三段 Swiss）

```powershell
python -m blinddraft.proto_match_v2 --field              # 32 席怎么来的
python -m blinddraft.proto_match_v2 --major "donk carry" # 跑完整一届
```

赛事外壳（§1~§2）在 v2 里独立实现，不 import `match.py`——v1 退役时不用拆
依赖。席位和分层直接复用 `ai_teams.build_pool_field`，也就是**区域 VRS 名额**
那一层，v1 / v2 拿到的是同一批队、同样的 8 / 8 / 16。

#### 修掉一个 v1 至今仍有的问题：VRS 分层被忽略

`build_current_field` 给每支队标了 `regional_stage`，但 v1 的 `run_major` 是按
Entry 排名切 `field[0:8] / [8:16] / [16:32]`，那个字段**算出来没人用**。实测
32 支里 13 支对不上：

| | VRS 排名 | v1 Entry | 区域名额给的 | v1 实际进的 |
|---|---:|---:|---|---|
| FUT | 4 | 59.8（第 22） | Stage 3 直邀 | **Stage 1** |
| Legacy | 6 | 65.1（第 12） | Stage 3 直邀 | Stage 2 |
| FlyQuest | 51 | 61.6（第 16） | Stage 1 | **Stage 2** |

§1.2 把区域名额表写死了（EU 8/6/6、AM 5/1/2、AS 3/1/0），所以 v2 里
**Stage 归属听 VRS，Entry 只排 Stage 内的种子**。两把尺子各管各的：VRS 回答
「凭什么拿到这个席位」，Entry 回答「同一层里谁更强」。

**v1 没改**，它还在服役、`/play` 还在用它，改了会动现有行为。这一条记在这里，
等 v2 接管时一起过去。

#### 玩家的 Stage 用哪把尺子

玩家是临时组的队，没有 VRS 积分，能衡量他的只有 Entry。所以：

> AI 的 Stage 由区域 VRS 名额定；玩家的 Stage 由 Entry 的**全场排名**定
> （前 8 进 Stage 3、9-16 进 Stage 2、其余 Stage 1），然后名额守恒逐级级联。

一开始试过「逐层挤」——Entry 高过某层最弱的就进那层。实测不成立：两把尺子的
秩相关只有 0.63，层间 Entry 重叠得很厉害（本届 Stage 2 最弱的 BIG 只有 61.5，
Stage 1 最强的 Astralis 有 81.4），那样一支 62 分的队能挤进 Stage 2 却比
Stage 1 半数队都弱。已改掉，回归测试盯着这条。

定下 Stage 之后仍然逐级级联：该层最弱的掉一级，下一层多一支、最弱的再掉一级，
Stage 1 多出来的那支失去席位。v1 那句「你的加入让下面几支各降一级」的叙事保住了。

#### 压力分四档

v1 只有三档（BO1 0 / BO3 1.0 / 生死局 1.25）。v0.3 §8.1 要求 Format 和 Pressure
分开，所以 v2 是：

| 局面 | 赛制 | 压力 |
|---|---|---:|
| 普通轮次 | BO1 | 0.0 |
| 2 胜，赢了就晋级 | BO3 | 0.8 |
| 2 负，输了就淘汰 | BO3 | 1.0 |
| 2-2 生死局 | BO3 | 1.2 |

赢一场就出线和输一场就回家，不该给同一个数。

#### 整届跑出来的分布

同一套阵容换 200 个 seed：

| 阵容 | Entry | 进场 | 进 Playoffs | 平均胜场 |
|---|---:|---|---:|---:|
| donk carry | 79.9 | Stage 2 | 20.5% | 4.54 |
| 五个普通职业哥 | 62.3 | Stage 1 | 0.0% | 1.58 |

弱队从 Stage 1 起步的分关晋级率（400 届）：Stage 1 过 11.2%，进了 Stage 2 之后
0/45。按单场胜率反推，连过两关的期望是 2.6 次，实测 0 次落在 p=6.6% 内，不是
bug——一支垫底队要连过两个 Swiss 本来就该很难。要放宽只有一个旋钮：MAP_SCALE。

### 回归闸门

`tests/test_star_visibility.py`，22 项，分三组：

- **v1（8 项）** 明星可见度、Carry 权重由卡面定死、逐人归因无残差。
- **`MatchV2Tests`（7 项）** 冻结的 Stability 分位数、§8.3 的三个压力例子、
  Leadership 的胜率目标区间（锁的是**胜率**不是分数，所以 MAP_SCALE 一变就会
  响）、Map Residual 不许碰 Player Story、BO3 更稳、Entry 里没有 L/E/S。
- **`MajorShellTests`（7 项）** 区域名额分层是 8/8/16 且**不许退化成按 Entry
  切**、玩家插队逐级级联且层级人数守恒、比全场都弱就 Failed to qualify、整届
  每支队都打到 3 胜或 3 负、晋级者带进下一层的是新实例（否则上一层战绩会被
  reset 擦掉，曾经真的出现过「Stage 1 晋级 MIBR(1-3)」）、四档压力、整届结果
  可序列化。

任何 Match Engine 改动都要先过它。

## 当前明确不做

- 不逐张人工维护第二份 AI 卡 JSON；AI 卡必须是生成物。
- 不因为 AI 当前数据好看就修改玩家卡的 Career Grade。
- 不用 KAST 直接生成 Stability。
- 不为了贴合 HLTV/VRS 排名反向篡改单个选手四维；队伍级异常走有理由的 `adjust`。
- 不在极简 Run 验证前扩淘汰赛、Buff、地图池或完整赛事 UI。
- 不以“整库相关性更高”替代玩家可解释性。

## 每次提交前的检查

- 改的是玩家卡、AI 当前卡，还是单场表现？只能属于其中一层。
- 是否引入了新的人工权威源？如果是，停止。
- 生成物能否从源码和人工层完整重建？
- 页面展示和 Match 实际读取的是不是同一份值？
- 这个改动会通过什么比赛事件被玩家感知？
