# 数据快照 — 2026-09-01

这份文档只回答一件事：**赛场上的 AI 对手，它们的"现在"是从哪来的。**

玩家抽到的卡是**生涯代表版本**（`data/draft_cards.json` v6，不动）。AI 对手要的是
**当前状态**，那是另一套数据，来自另外几个源，走另一套刷新节奏。两者只共享
"这个人是谁"，不共享任何数值语义。

---

## 一、五个源，各管一件事

| 文件 | 管什么 | 来源 | 刷新 | 生成器 |
|---|---|---|---|---|
| `data/players.json` | 选手身份、国籍、Major 履历、当前队/角色/状态 | Liquipedia | 手动 | `scraper/build_db.py --refresh-existing` |
| `data/draft_cards.json` | **玩家抽的卡**（生涯代表版本，v6） | 由上者生成 | **冻结** | `scripts/gen_draft_cards.py` |
| `data/team_snapshot.json` | **当前阵容 + 队内位置 + 两套排名** | 5eplay | 手动 | `scraper/fetch_rankings.py --teams` |
| `data/5e_player_stats.json` | **当前个人竞技数据**（rating/adr/kast…） | 5eplay | 手动 | `scripts/fetch_5e_stats.py` |
| `data/vrs_global.json` | 官方 VRS，**只做交叉核对** | Valve GitHub | 月更 | `scraper/fetch_rankings.py --vrs` |

`data/hltv_top100.json` 是更早的手工快照（2026-07-13），只有名次没有积分。
`team_snapshot.json` 里的 `hltv_rank` / `hltv_points` 已经覆盖了它的用途，
而且是周更的。旧文件暂时保留，因为 `server/rankings.py`（猜选手那边）还在用它，
里面的 `aliases` 段是人工维护的队名对照。

## 三、踩过的坑（这一节比上面都重要）

### 3.1 不要用 VRS 的阵容

Valve 官方 VRS 是**月更**的。到 2026-09-01，最新一版是 `2026_08_03`，落后近一个月：

```
VRS 2026-08-03                          5eplay 2026-09-01（真实）
G2:  ... SunPayus                       G2:  ... r1nkle
The MongolZ: 910 bLitz cobrazera        TheMongolz: bLitz Techno 910
             mzinho Techno                          tikuak DarkMeister
BC.Game:  electroNic Magisk mzinho ...  （mzinho 已不在 MongolZ）
```

**`mzinho` 同时出现在两支队里，那就是数据过期的直接证据**，不是需要去重的脏数据。
我一度只把它当成"要处理的冲突"，差点拿这份当权威阵容。

VRS 仍然抓一份，但**只做积分口径的交叉核对**，阵容一律以 `team_snapshot.json` 为准。

### 3.2 位置字段：无序、不排他、还有缺口

5eplay 的 `positions` 和 Liquipedia 的 `roles` 一样是**无序的角色集合**，
取第一个会把 ZywOo（`['步枪手','狙击手']`）判成步枪手——和设计稿 §46.2 同一个坑。

但"队内角色表"这个更好的输入，单独用还是不够。实测两种失效方式：

```
不排他：Legacy 的 latto / dumau / try 三个人都标了「狙击手」
有缺口：FaZe 五个人没有一个标「指挥」，而 Twistzz 就是指挥
```

所以 `resolve_roles` 同时看两个源，规则是**队内优先、生涯兜底、独占者优先**：

1. 有人标了该 tag，就只在这些人里挑；一个都没有，才拿 Liquipedia 的生涯角色
   兜底。**队内角色永远压过生涯角色**，因为前者说的是"现在"。
2. 同 tag 多人时按"该源里只有这一个 tag"决胜：`try` 只标狙，latto 标了
   步枪+狙，所以狙是 try 的。两边都平才看 top20 次数。
3. 找不到人就**如实留空**，写进 `role_gaps`，不假装。Liquid 五个人没人标狙，
   Inner Circle 没人标指挥——那就是没有，硬指一个才是错。

改完 288 支里改判 18 处，前 25 名占 6 处：latto→步枪 / try→狙、
Twistzz→指挥、s1zzi→狙、REZ↔hypex 对调。7 处走了 Liquipedia 兜底，
201 支有留空（绝大多数是首发不满五人的小队）。

### 3.3 教练混在 players 里

`positions` 含「教练」的人也在 `overview.players` 中。不剔掉就会顶掉一个首发位置，
正是 §46.4 那个坑（gla1ve 挂 coach 却被算成 100 Thieves 的队员）。

### 3.4 队伍列表接口不全，要从选手页反查

`mfilter/team/list` 只收录近期有比赛数据的队，238 支里没有 BC.Game。
而 `players/<id>` 的 `basic_info.team_id` 是权威当前队伍——**反过来走**：
我们关心哪些选手，就能发现哪些队。这样发现集合天然等于"卡库里的人现在所在的队"。
`--discover` 就是这一步，把 id 表从 238 补到 288。

顺带：BC.Game 的 id 是 `hltv_team_12878` 而不是 `csgo_tm_*`，两个命名空间并存。

### 3.5 队名不一定对得上

`The MongolZ` 在 5eplay 叫 `Mongolz`。按名字精确查会查空，我因此一度以为它不在
快照里。**队名匹配一律要归一化**（`server/rankings.py` 已经有 `normalize_team_name`）。

### 3.6 翻排行榜会静默丢数据

见设计稿 §52.1。`sort_key=rating` 并列太多，页边界每次都漂，抓 1494 行只有
1129 个唯一 id，两次抓漏的人还不一样。**逐人查 `player_id` 才是对的做法**，
根本不经过分页。

### 3.7 leet 规整会撞名，而撞名比漏掉更危险

`norm()` 把 `1→i 0→o 3→e 4→a 5/$→s 7→t` 之后拿去查 id 表，实测 **29 组撞名**：

```
BL1TZ / bLitz      NiKo / niko      b1t / BIT      FROZ3N / frozen
alex666 / alex     n1cks / nicks    m1N1 / mini    P4TriCK / Patrick
```

原来是 `setdefault` 先到先得，于是 **bLitz 拿到了 BL1TZ 的 id**。那个 id 查出来
没有顶级赛事样本，脚本如实记成"这人没打过 S 级赛"——**一条看起来完全正常的
结论，实际指着另一个人**。`Alex (Spanish player)` 更糟：它一直指着 B8 的
alex666，还真返回了数据。

静默配错人比漏掉严重得多，因为漏掉会出现在"对不上"清单里，配错不会。修法：

- **id 的权威来源是队伍快照**（`teams/<id>/overview` 列出来的人自带 id），
  那一层根本不经过名字匹配，不可能配错。
- 名字索引改成**三档由严到宽**：原名 → 忽略大小写 → leet 规整。`NiKo` 和
  `niko` 在第一档就分开了，走不到会撞的那档。
- 三档都分不开的（两个真同名的 `mds`、`ADK`、`space`、`roman`）**整组丢掉**，
  留给人工去 `5e_aliases.json` 里直接钉 `player_id`。

结果：匹配率 97% → **99%（307/311）**，捞回 bLitz / s1zzi / Zero / Lucky，
纠正 Alex 一处配错人。bLitz 的行现在和页面抓包逐字段一致
（rating 0.99、164 图、kddiff −279）。

## 四、口径

- **快照日** 2026-09-01。VRS 取"不晚于快照日的最新一版"，所以同一个快照日重复
  跑结果一样；5eplay 是实时的，只能盖抓取时间——这是它比 VRS 新的代价。
- **只合并不删除。** `fetch_5e_stats.py` 里写死了这条：抓失败的人保留旧值并标
  `stale`，绝不消失，跑完打印五个计数。教训来自 `data/images.json`（抓图 SSL
  失败就把条目删了）。**每次刷新后和 HEAD 对 diff，应当只增不减。**
- **人工层**在 `data/manual/`，部署时不覆盖：`5e_aliases.json`（昵称对照）、
  `major_field.json`（赛场配置）。
- **不动的东西**：卡库 v6、`gen_draft_cards.py`、玩家抽到的卡。

## 五、还没接上

队伍快照里的**当前阵容和队内位置**目前还没接进 `scripts/proto_ai_teams.py`——
那一层仍然从卡上的 `team` 字段拼阵容、从 Liquipedia `roles` 猜位置、再做全队去重
（§46.2、§46.6、§49、§50 一整套）。接上之后那一整套可以退役掉大半，
因为"谁在这支队、谁在喊、谁拿狙"变成了查表而不是推断。

个人竞技数据（`rating`/`kast`）也还没接进四维，映射曲线和收缩系数未定，见 §52.6。

## 六、名册边界：卡库能覆盖到第几名

AI 对手的名册现在是"按 HLTV 排名取前 N 支真实队伍"。但**卡库是 649 个打过
Major 的人**，当前排行榜前排里有大把人从没打过 Major，甚至整支是新队。
覆盖率随名次掉得很快：

| 名次段 | 首发满五人 | 卡库覆盖 | 五人全有卡 |
|---|---|---|---|
| #1–10 | 10 支 | **100%** | 10 支 |
| #11–20 | 10 支 | 78% | 5 支 |
| #21–30 | 9 支 | 69% | 2 支 |
| #31–50 | 17 支 | 62% | 7 支 |
| #51–100 | 21 支 | 40% | 1 支 |

前十名一个洞都没有；从 #12 开始出现缺口（FaZe 缺 JBOEN/Neityu，
The MongolZ 缺 Techno/tikuak/DarkMeister，magic 五个人缺四个）。

**"五人全有卡"的队恰好 25 支，最深到 #57**：

```
Spirit Falcons FURIA Vitality MOUZ FUT Legacy NAVI G2 Aurora 9z
Astralis B8 BB GamerLegion BIG Lynn Vision M80 DENDELE TYLOO
Luminosity NRG BC.Game SINNERS Imperial
```

25 支差不多就是一个 Major 的规模，而且这条线**不是拍脑袋定的**：一个人没有卡
是因为他没打过 Major，一支凑不齐五个 Major 老兵的队本来也不该出现在 Major
名册里。**卡库的边界和这个虚构世界的边界是同一条线。**

代价要说清楚：这条线会把 FaZe(#12)、The MongolZ(#14)、PARIVISION(#17)、
paiN(#19)、3DMAX(#21)、Liquid(#22) 挡在外面——它们是真队、也真的强。
`major_field.json` 里已经有 per-team `max_filler` 这个豁免口子，
想把某支队请回来就在那儿单独放宽，而不是全局放宽。

三条路，未定：

- **A 收紧**：默认 `max_filler: 0`，名册就是上面这 25 支，个别队人工豁免。
- **B 维持**：`max_filler: 1~2` + G1 占位。代价是 The MongolZ 由三个虚构 G1
  组成，那已经不是 The MongolZ 了。
- **C 补库**：给前 30 名队伍里没打过 Major 的人补卡（约 30 人）。这会突破
  "649 人都打过 Major"这条设定，得先想清楚卡的 grade 怎么给。
