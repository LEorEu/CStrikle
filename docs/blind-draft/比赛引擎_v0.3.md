# FribergCS2 Blind Draft — Match Engine 设计稿 v0.3

> **状态：第二轮重构 / 替代 v0.2**
>
> **定位：真实 Major 外壳 + 可解释的极简比赛引擎**
>
> v0.1 的赛事骨架基本成立，但比赛数值层已经出现结构性问题：
>
> - Entry 同时静态计入 Firepower / Leadership / Experience / Stability；
> - Stability / Experience / Leadership 又在比赛过程中再次生效，形成“双重收费”；
> - Player Form、Team Shared Form、最终 Logistic 胜负骰叠了多层随机；
> - 当图火力重新排序后，低基础高波动选手容易抢到明星权重；
> - MVP 与 LIFE GAME 的语义混在一起，导致 donk / ZywOo 这种超级明星反而缺乏存在感。
>
> v0.3 的目标仍然不是把 CS 做成完整 Round Simulator，而是在实测基础上把“个人表现随机”和“地图级未建模随机”彻底分层：
>
> > **Firepower 决定“能打多高”；Stability 决定“这张图兑现多少”；Experience 只处理压力；Leadership 只处理团队执行。**
>
> 同一个变量只能在一个主要层级做功一次。

## 本轮 v0.3 的关键订正

v0.2 的方向基本正确，但原型实测又暴露了三个必须写回设计稿的事实：

1. **五人独立 Roll 仍然会被队伍聚合强烈抹平。** 个人单图波动看起来很大，并不代表 Team Performance 也有足够方差；当前权重聚合后队伍单图 σ 约只有 3 左右。
2. **不能同时删除 Team Shared Form 与最终宏观随机，然后直接比大小。** 实测 Entry +5 时强队胜率接近 99%，整个 Major 会退化成按 Entry 排序。
3. **Leadership / Chem / Buff 的“分值大小”不能脱离最终传递函数单独拍。** 当胜负曲线很陡时，±2~3 Strength 并不“小”。以后所有队伍层 modifier 都应先定义“希望贡献多少胜率”，再反推 Strength。

因此 v0.3 正式定下：

> **保留 10 个 Player Performance RNG + 1 个 Map Residual RNG。**
>
> Player RNG 解释“谁今天打得好”；Map Residual 解释“这张 CS 地图里我们没有展开模拟的回合级变量”。

---

# 0. v0.3 的五条总原则

## 0.1 比赛首先是 5v5 的枪战

任何模型都不能把下面这个事实算没：

> **三把世界级枪 + 两个弱点，首先应该是一支火力很强、但结构有缺陷的队。**

它可以因为缺 IGL、缺 AWP、默契差、高压局 Choke、核心失常、战术执行弱或未建模的地图/经济/timing 因素而输掉比赛。

但不能在比赛开始之前，因为 Experience / Stability / Leadership 低，就把 donk / ZywOo 的火力提前折算掉一大半。

## 0.2 四维各做一件事

| 维度 | 核心语义 | Entry 静态加权 | 当图作用 |
|---|---|---:|---|
| **Firepower** | 正常状态能打多高 | **是，主体** | 决定 Player Performance 基线 |
| **Stability** | 正常火力的兑现可靠性 | **否** | 决定单图 Performance Roll 的分布 |
| **Experience** | 压力来了还能兑现多少 | **否** | 只在 Pressure > 0 时修正个人表现 |
| **Leadership** | 队伍战术与执行质量 | **否** | 小幅修改 Team Execution |

禁止再出现：

```text
Entry = F×40% + L×20% + E×20% + S×20%
```

## 0.3 一张图，每名选手只有一次“个人发挥随机”

Player Performance 的唯一随机源就是：

> **这张图他实际打出了多少 Firepower。**

Stability 决定这个 Roll 的分布形状。

Pressure / Experience 不再另掷一个 Choke 骰，而是修改同一次 Roll 的结果或分布。

## 0.4 比赛必须保留一层 Map-level 不确定性

实测已经确认：

```text
个人 σ ≈ 8~10
        ↓ 五人加权聚合
Team Performance σ ≈ 3
```

因此“五个人已经各自 Roll 过，所以不再需要地图级随机”的前提不成立。

如果删除 Team Shared Form，同时也删除最终宏观随机，直接比较双方 Team Performance：

```text
Entry +2  → 强队约 82.6%
Entry +5  → 强队约 99.0%
Entry +10 → 几乎 100%
```

这不是我们想要的 CS。

所以 v0.3 正式保留：

> **Map Residual / 未建模比赛变量**

它代表当前引擎没有展开模拟的：

- 地图适配；
- 手枪局；
- 经济与连败奖励；
- timing；
- clutch；
- CT/T；
- 关键首杀；
- 局内战术克制；
- 关键回合的偶然事件。

它不是 Player Form，也不进入 MVP；它只是把尚未做成 Round Engine 的 CS 内容压缩成一个 Map-level 残差。

## 0.5 比赛故事和比赛结果必须分开

- **MVP**：谁实际表现最好；
- **LIFE GAME**：谁远超自己的基础能力；
- **UNDERPERFORM**：谁明显低于自己的基础能力；
- **Winner**：两队整体表现 + 战术执行 + Map Residual 的结果。

因此完全允许：

> ZywOo 是全场 MVP，但法国班子仍然输掉比赛。

# 4. Entry：只表示纸面战斗力

## 4.1 Entry 的新定义

```text
Entry Strength
= Base Team Firepower
+ Native Chemistry Modifier
+ Roster Structure Modifier
+ Entry-eligible Trait / Rogue Modifier
+ Manual Team Adjust（仅异常兜底）
```

不再静态加入：

- Stability；
- Experience；
- Leadership。

## 4.2 Base Team Firepower

暂时保留明星层级聚合：

```text
Top Firepower × 35%
Second Firepower × 25%
Remaining Three Average × 40%
```

等价：

```text
F1 × .35
+ F2 × .25
+ F3 × .1333
+ F4 × .1333
+ F5 × .1333
```

### Carry Hierarchy 固定

F1 / F2 / F3... 按 **Base Card Firepower** 排定。

比赛过程中即使：

```text
F55 → 78 LIFE GAME
```

也不会临时抢走 F96 选手的 `.35` Carry Weight。

原因：

> 一张图突然手热，不代表整支队的战术资源与核心定位立即改写。

## 4.3 是否以后改成五人平均？

暂时不动。

v0.3 先固定 Carry Hierarchy，再重新测。

如果后续明星权重过强，再单独比较：

- 35 / 25 / 40；
- 30 / 22 / 48；
- 五人平均。

不要与其他机制同时修改。

# 5. Roster Structure

这一层只处理客观阵容结构，例如：

- 无 AWP；
- 无 IGL；
- Multiple IGL；
- 特殊 Role Conflict。

原则：

> **一个缺陷只收费一次。**

NO IGL 有两种实现：

### A. Entry 直接扣分
比赛中 Leadership 不再额外给负分。

### B. Entry 不扣
比赛中因缺少 IGL 得不到正常 Team Execution。

v0.3 推荐先选 **B**，因为更符合 Leadership 的语义。

无 AWP 可以继续保留 Entry 级的小幅结构惩罚，例如现有 `-4`，但需重新随新 Entry 标尺校准。

# 6. Stability：单图发挥的核心机制

v0.1：

```text
delta ~ Normal(0, sigma)
sigma = (100 - Stability) / 4
```

问题：

- 均值完全对称；
- 低稳定只是“更疯”，长期并不更差；
- 弱卡由于方差大，更容易获得夸张 LIFE GAME；
- 高 Firepower + 高 Stability 的超级明星反而缺乏向上故事。

v0.3 改为：

> **Stability = Firepower 的兑现率 + 波动性。**

## 6.1 目标分布

假设 `Firepower = 80`。

高 Stability：

```text
多数：78 / 81 / 83 / 85
少数：73 / 90
极少大崩
```

低 Stability：

```text
经常：62 / 68 / 73 / 77
有时：82 / 86
极少：94 / 98 LIFE GAME
```

因此：

> **高稳定：更经常打出 Base 或略高于 Base，负面尾巴短。**

> **低稳定：更经常低于 Base，但拥有更长的正负尾巴。**

## 6.2 一次 Roll 的实现要求

不要增加第二个随机数。

推荐用一个 Uniform `u` 完成：

1. Stability 决定 `P(up)`；
2. 同一个 `u` 决定落在正区还是负区；
3. Stability 决定对应尾巴的幅度；
4. 输出唯一一个 `delta`。

参数不要现在写死。

第一轮只要求：

```text
Stability ↑
→ P(delta >= 0) ↑
→ downside tail ↓
→ ordinary variance ↓

Stability ↓
→ P(delta >= 0) ↓
→ downside tail ↑
→ upside tail ↑
```

## 6.3 v0.3：当前 Stability 分布暂时冻结

原型已经复现出接近目标的边际分布：

```text
F80 / S90:
p5 ≈ 75
median ≈ 81
p95 ≈ 87
p99 ≈ 90

F80 / S50:
p5 ≈ 63
median ≈ 78
p95 ≈ 93
p99 ≈ 98
```

明星可见性测试也明显改善：

```text
donk  F96 / S87 → MVP ≈ 89.6%
spaze F50 / S47 → MVP ≈ 0%, LIFE GAME ≈ 6%
```

因此当前阶段明确：

> **不要再为了宏观爆冷率去放大 Player Stability 的分布宽度。**

实测把宽度放大到 4 倍虽然能把 +10 弱队爆冷率拉回旧版附近，但会出现：

```text
F80 / S50 → 单图约 11 ~ 130
```

这会直接破坏 Player Story。

以后如果 BO1 爆冷率不够：

> **调 Map Residual，而不是重新把个人表现搞疯。**

是合法结果。

## 7.1 Soft Cap

v0.1 的 `99+` 强压缩可能过度限制超级明星的正面表现。

# 8. Experience：只在压力场景生效

Experience：

> **不进入 Entry。**

> **不参与普通状态 Roll。**

它只回答：

> **压力来了以后，这个人还能不能把本来的表现打出来。**

## 8.1 Format 与 Pressure 必须分开

BO1 本身不自动等于高压。

建议 Pressure 由赛事语境决定：

| 场景 | Pressure（初始建议，未锁） |
|---|---:|
| 普通 Swiss | 0 |
| Advancement | 0.7–0.9 |
| Elimination | 0.9–1.1 |
| 2-2 Decider | 1.1–1.3 |
| Quarterfinal | 1.1–1.3 |
| Semifinal | 1.3–1.5 |
| Final | 1.5–1.8 |

## 8.2 Choke 必须逐人发生

不要再用 Team Average Experience → 全队统一 -X。

应该：

```text
Player Raw Performance Roll
        ↓
Pressure > 0 ?
        ↓
根据该球员 Experience 修正
        ↓
Effective Firepower
```

低 Experience：

> 在 Pressure 下更容易放大负面结果 / 更难兑现正面结果。

高 Experience：

> 尽量保持原始 Performance。

## 8.3 不增加 Choke RNG

Experience 修改同一次 Performance Roll。

例如：

```text
Player A
Raw delta = -7
EXP 25
Pressure 1.2
→ final delta = -11

Player B
Raw delta = -7
EXP 90
Pressure 1.2
→ final delta ≈ -7 / -8
```

数字仅示意。

# 9. Leadership：只表示团队执行

Leadership：

> **不进入 Entry 的 20% 总分。**

> **不再同时修改 Form、Choke、Chem、Variance 等多个系统。**

v0.3 第一版只做：

> **Team Execution Modifier**

## 9.1 Team Leadership

有 IGL：

> 使用当前 / Career 对应语境下的主 IGL Leadership。

无 IGL：

> `NO IGL`，不给正常 Team Execution。

多个 IGL：

> 不叠加，可触发 Role Conflict / Trait。

## 9.2 Leadership 不再用“±几分看起来不大”校准

v0.2 曾建议：

```text
L95 elite IGL  → +2.5
NO IGL         → -3
```

实测证明这个口径不可靠。

在缺少平滑的 Map-level 传递函数时，`+2.5 / -3` 足以把五五开附近的胜率拉到约：

```text
elite IGL → 65% 左右
NO IGL    → 26% 左右
```

所以从 v0.3 开始，Leadership、Chemistry、Roster Buff 等所有 Team Modifier 都采用同一原则：

> **先定义它应该贡献多少“胜率差”，再根据最终 MAP_SCALE 反推 Strength Modifier。**

第一轮设计目标可先使用：

```text
elite IGL vs average IGL
→ 在五人火力完全相同时，单图增加约 4~6 个百分点胜率

NO IGL vs average IGL
→ 单图降低约 6~10 个百分点胜率
```

具体对应多少 Strength，必须等 `MAP_SCALE` 确定后计算，不提前锁 `+2.5 / -3`。

## 9.3 暂时不要让 Leadership 缓冲 Choke

第一版明确分工：

```text
Experience → individual pressure resistance
Leadership → team execution
```

如果未来测试证明顶级 IGL 在高压局仍缺少价值，再增加：

```text
Leadership × Pressure → small team relief
```

作为后续版本。

# 10. Chemistry

Chemistry 继续存在，但只做一次。

v0.3 推荐：

> **Chemistry 作为 Baseline Coordination，进入 Entry / Team Baseline。**

比赛过程中不要再第二次因为 Chemistry 增加同一份分数。

> 修改这一层的值或 cap，而不是再额外加一层 Overall。

旧 `CHEM_CAP=4` 不自动继承为最终值，需要在新版 Entry 标尺上重新扫描。

# 12. Team Shared Form：退役

v0.1：

```text
TEAM_FORM_SHARE = 0.65
```

原因是五个人独立 Roll 后平均会把波动按 √5 抹平。

这个观察没错，但 v0.3 不再用 Team Shared Form 解决。

原因：

1. 它让五个人经常整队一起爆 / 一起崩；
2. 它和最终 Logistic Winner RNG 都在承担“队伍级未知变量”；
3. 新版 Entry 不再把 Firepower ×0.4；
4. 队伍层面的未建模随机统一交给 **Map Residual**。

因此：

> **Team Shared Form 删除。**

# 13. Map Residual：替代最终胜负骰

## 13.1 为什么不能直接比 Player Strength

实测：

| Entry 领先 | 旧引擎 | 只删 Winner RNG | Winner RNG + Shared Form 都删 |
|---:|---:|---:|---:|
| 2 | 53.8% | 69.4% | 82.6% |
| 5 | 59.5% | 89.7% | 99.0% |
| 10 | 68.3% | 99.4% | 100% |
| 20 | 82.3% | 100% | 100% |

删除所有宏观随机后：

> **Major 退化成按 Entry 排名的表格。**

因此 CS 中大量尚未建模的变量必须有一个统一出口。

## 13.2 新定义

每张地图最后生成一次：

> **Map Residual**

```text
Player Performance Difference
+ Leadership / Team Modifiers
+ Map Residual
= Final Map Margin
```

然后：

```text
Final Map Margin > 0 → Team A Win
Final Map Margin < 0 → Team B Win
```

不再额外 Bernoulli Roll Winner。

## 13.3 推荐分布与当前校准区间

实现可以继续使用：

```text
MapResidual ~ Logistic(0, MAP_SCALE)
```

它与经典 Logistic Win Probability 在统计意义上等价：

```text
P(A Win)
= logistic((StrengthA - StrengthB) / MAP_SCALE)
```

区别只是架构解释：

```text
v1:
Strength Diff → Win Probability → Bernoulli Winner

v0.3:
Strength Diff + Map Residual → Final Margin → Winner
```

两者数学上可以接近，但 v0.3 明确规定 Residual 属于“地图内未建模事件”，而不是 Player Story。

### 订正（原型实测，2026-09-03）

上面那个等价式**只在“双方 Team Performance 是常数”时成立**。实际 StrengthA /
StrengthB 各自含 Player 波动（两队之差 σ ≈ 4.3），Map Residual 自己 σ ≈ 10.9，
最终胜率曲线是两者的**卷积**，比 `logistic(gap / MAP_SCALE)` 更平：

| 火力差 | 实测（整套引擎） | logistic(gap/6) | 反解等效 scale |
|---:|---:|---:|---:|
| +2 | 57.0% | 58.3% | 7.06 |
| +5 | 67.5% | 69.7% | 6.83 |
| +10 | 81.8% | 84.1% | 6.66 |
| +20 | 95.8% | 96.6% | 6.40 |
| +30 | 99.1% | 99.3% | 6.36 |

等效 scale 不是常数，随分差从 7.1 漂到 6.4——整条曲线连 logistic 形状都不是。
因此：

> **MAP_SCALE 只控制 Residual 这一层，它不等于整套引擎的胜率曲线。
> 任何胜率结论都必须靠 Monte Carlo 实测，不能由 MAP_SCALE 解析推导。**

这条对 §9.2 那个「先定胜率差再反推 Strength Modifier」的规矩同样适用：反推用的
换算率（当前 MAP_SCALE=6 下约 1 分 Strength ≈ 3.5 个百分点）本身是跑出来的，
而且 MAP_SCALE 一动就必须重跑。

好消息是曲线更平意味着同样手感下 MAP_SCALE 可以取得比纯反推更小。

旧 `WIN_SCALE = 13` 不再作为迁移默认值。

原因：新版已经有更有效的 Player Performance 波动；如果仍使用 13，很可能重新让最终随机淹没选手层。

当前优先扫描：

```text
MAP_SCALE = 4 / 5 / 6 / 7
```

先锁定 Player Stability 分布，再只调这个宏观旋钮。

目标不是复刻 v1，而是找到一个中间点：

- +2 的队伍只是小优；
- +5 明显有优势但远非必胜；
- +10 已经是强 Favorite，但 BO1 仍可爆冷；
- +20 极难翻，但不应机械 100%。

### 扫描结果（原型 `--tune`，2026-09-03）

| MAP_SCALE | +2 | +5 | +10 | +20 | +10 时 BO1 爆冷 |
|---:|---:|---:|---:|---:|---:|
| 4 | 59.2% | 72.7% | 88.7% | 98.8% | 11.3% |
| **6** | **56.7%** | **67.0%** | **81.2%** | **95.9%** | **18.8%** |
| 7 | 55.5% | 65.1% | 78.0% | 93.6% | 22.0% |
| 9 | 54.5% | 62.4% | 72.9% | 88.9% | 27.1% |

**取 6**：四条目标同时满足。4 太陡（+5 就 72.7%），9 太平（+10 才 72.9%，
强队没有分量）。

## 13.4 Map Residual 不参与 Player Story

它绝对不能：

- 生成 MVP；
- 生成 LIFE GAME；
- 改 Player Effective Firepower；
- 让一个 F55 选手因为 Residual 成为“比赛最佳”。

它只影响：

> **队伍为什么在整体表现之外仍然可能输赢。**

第一版可以只在 Debug 页面展示。

## 13.5 已确认的“三选二”问题，以及 v0.3 的取舍

原型显示，如果只允许 Player Roll 决定最终胜负：

1. 保持当前合理的 Stability 边际分布；
2. 直接比较双方 Team Performance；
3. 保持像样的 CS 爆冷率；

三者无法同时满足。

尝试过两种补救：

### 放大 Player Variance

可以提高爆冷，但会把 F80 / S50 推到荒谬的 11~130 区间。

### 恢复强 Team Correlation

边际分布不变，但即使相关性拉到很高，爆冷提升仍有限，而且会重新出现整队一起爆 / 一起崩。

因此 v0.3 的明确取舍是：

> **保留当前 Player Distribution，删除 Team Shared Form，增加一个独立 Map Residual。**

换句话说：

> **不要要求“选手今天的状态”解释 CS 比赛里的全部随机。**

# 15. Map Simulation Pipeline

```text
1. Read Base Cards / Current Profiles

2. Fix Carry Hierarchy
   by Base Firepower

3. For each player:
   Stability → one Performance Roll
   Pressure + Experience → modify same roll
   → Effective Firepower

4. Aggregate five Effective Firepowers
   using FIXED carry weights

5. Apply Team Execution
   from Leadership

6. Apply map-eligible Trait / Rogue modifiers

7. Draw one Map Residual

8. Final Map Margin
   = Team A Performance
   - Team B Performance
   + Residual

9. Margin > 0 → Winner
```

注意：

> Entry-level Chemistry / Structure 如果已经体现在 baseline 中，不要在第 5/6 步再重复加。

# 23. Round Engine：长期需要，但绝不能真的模拟完整 CS

v0.3 的结论不是：

> “Round Engine 没价值。”

恰恰相反，当前 Map Residual 之所以必须存在，就是因为真正决定一张 CS 地图的很多内容都发生在 Round 层。

但项目不应该真的去模拟：

```text
每回合买枪
每人站位
每颗道具
每次对枪
每次转点
每个残局
```

那会从 Blind Draft 游戏变成另一个项目，而且会制造更大量无法验证的假精确。

## 23.1 未来如果做，只做“极简 Round Engine”

目标不是复刻 CS2，而是把 Map Residual 中最重要、玩家最容易理解的部分拆出来。

可以考虑每张图只模拟若干宏观 Round Phase，例如：

```text
Pistol / Opening
      ↓
Early Economy
      ↓
Gun-round Core
      ↓
Late / Clutch
```

或者更简单：

```text
13 个抽象 Round Tokens
```

每个 Token 只读取：

- 当前 Team Firepower；
- IGL / Team Execution；
- 简单 Economy State；
- 少量 Map / Side modifier；
- 一个 Round Residual。

最终从这些抽象局得到 Map Winner。

这仍然不是“真实逐回合模拟”，而是比单一 Map Residual 多一层结构。

## 23.2 什么时候值得做

只有当 v0.3 已经满足：

- Draft 本身好玩；
- Major 流程稳定；
- Match Engine 的明星叙事合理；
- Map Residual 参数已经校准；

之后，玩家仍然明显觉得：

> “比赛结果太像一个黑箱 Map Roll。”

才进入极简 Round Engine。

现阶段不要为了“让模型看起来更真实”继续扩复杂度。

# 24. Map Residual 的长期演化路径

v0.3：

```text
Player Performance
+ Leadership
+ Chemistry / Buff
+ Map Residual
```

以后增加真实 Map Pool：

```text
Player Performance
+ Leadership
+ Map Matchup
+ smaller Residual
```

以后增加 BP：

```text
Player Performance
+ Leadership
+ Map / BP
+ smaller Residual
```

以后增加极简 Round Engine：

```text
Player Performance
+ Leadership
+ Map / BP
+ Abstract Round Flow
+ much smaller Residual
```

因此 Map Residual 的正确定位是：

> **一个可以被未来真实机制逐步“吃掉”的误差桶。**

它现在大，不代表设计失败；只代表我们有意识地没有伪装成已经模拟了经济、手枪、地图与关键局。

# 25. 一句话版本

> **Match Engine v0.3 不再先把四维压成一个 Overall，再让它们重复生效。**

它变成：

```text
Firepower
    ↓
Stability：这张图打出多少
    ↓
Experience：压力下能保住多少
    ↓
五人固定 Carry Hierarchy 聚合
    ↓
Leadership：队伍执行
    ↓
Chem / Trait / Rogue
    ↓
Map Residual：当前尚未拆成 Round / Map 机制的 CS 细节
    ↓
Winner
```

最终希望玩家看到的不是：

> “我的 Entry 65.7，对面 65.1，然后 51%，输了。”

> **“这队纸面三把枪明显更硬；donk 正常发挥，molodoy 打得不错，但低经验的两个队友在淘汰局掉了状态，对面又拿到了关键 Map Swing，最后输掉了这张图。”**

或者：

> **“法国班子最终输了，但 ZywOo 三张图拿了两次 MVP——问题不是他没打出来，是这套阵容整体没能把他的表现转化成胜利。”**

只要引擎能稳定地产生这种可解释结果：

> **Road to Major 的比赛层就成立了。**
