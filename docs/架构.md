# 仓库架构

这个仓库有**两个游戏**，共用**一份选手库**。

拆包之前它们是混在一起的：所有代码平铺在 `server/` `scripts/` `scraper/` 四个
目录里，按「这是个脚本还是个服务」分，而不是按「这属于哪个游戏」分。后果不是
抽象的——

- Blind Draft 的卡牌生成器 `from server.players import PlayerDB`，反过来伸手
  进了猜选手的服务端包；
- 猜选手的生产镜像 `COPY scripts ./scripts`，把整套 Blind Draft 原型
  （包括后来那 12 MB 的 5E 选手照片）一起打了进去；
- 「改猜选手会不会弄坏 Blind Draft」没人答得上来，因为没有任何东西定义过边界。

现在按**归属**分，边界由 [`tests/test_architecture.py`](../tests/test_architecture.py)
钉住。

---

## 一、三层，依赖只往下

```
                  ┌─────────────────────────────┐
                  │  playerdb                   │  共享底座
                  │  选手库 · 赛区 · 排名 · 爬虫 │  不依赖任何内部包
                  └─────────────────────────────┘
                     ▲                    ▲
         ┌───────────┴──────────┐   ┌─────┴──────────────┐
         │  猜选手（已上线）      │   │  Blind Draft（在做）│
         │  server ↔ gtptools   │   │  blinddraft        │
         │  static              │   │    ▲        ▲      │
         └──────────────────────┘   │  bdtools  bdserver │
                                    └────────────────────┘
```

**两条硬约束**，写成了测试，改坏了会红：

1. `playerdb` 不依赖任何内部包。它是底座，谁都能用它，它谁都不用。
   一旦它反向依赖上层，`import playerdb` 就会把两个游戏都拖进来。
2. 猜选手一侧（`server` / `gtptools`）不许出现 `blinddraft` / `bdtools`。
   Dockerfile 敢不把 `apps/blind_draft` 放进镜像，靠的就是这一条；
   违反了不会在本地报错，只会在**线上** ImportError。

`server ↔ gtptools` 是互相依赖的（管理页要调 `sync_hltv_roles`，benchmark 要
调 `server.ai_player`）。同一个 app 内部，允许。

`bdserver` 单向依赖 `blinddraft`，反过来不行：玩法代码一旦 import 后台，
命令行跑一局就要顺带拖起 FastAPI。

---

## 二、包名与目录

文件按 `apps/` + `packages/` 摆，但 import 名是**扁平**的——靠
[`pyproject.toml`](../pyproject.toml) 的 `package-dir` 映射：

| import 名 | 目录 | 是什么 |
|---|---|---|
| `playerdb` | `packages/playerdb/` | 共享选手库：`Player`/`PlayerDB`、赛区表、队名归一、Major 战绩 |
| `playerdb.scrape` | `packages/playerdb/scrape/` | 建库与抓图的爬虫。**单独一个子包，因为它不进运行时镜像**（见第六节） |
| `server` | `apps/guess_the_player/server/` | 猜选手运行时（FastAPI） |
| `gtptools` | `apps/guess_the_player/tools/` | 猜选手的本地工具：HLTV 角色同步、AI 对手 benchmark |
| `blinddraft` | `apps/blind_draft/blinddraft/` | Blind Draft 玩法：卡库、选人、入场、比赛引擎、AI 对手 |
| `bdtools` | `apps/blind_draft/tools/` | Blind Draft 的抓取与导出工具 |
| `bdserver` | `apps/blind_draft/server/` | Blind Draft 的**本地调参后台**（FastAPI）：卡牌页可改人工层，AI 对手页只读。不上线 |

**为什么要这层映射**，两个具体理由：

- `apps/guess-the-player` 这种带连字符的目录不能当 Python 模块路径；
- 生产入口是 `uvicorn server.main:app`。映射之后这一行、compose 的卷路径、
  部署脚本**一个字都不用改**，目录重排对线上完全透明。

装一次就行，装完各文件顶上那些 `sys.path.insert(...)` 就都删掉了：

```powershell
pip install -e .
```

## 三、共享的到底是什么

只有一样东西是真共享的：**`data/players.json`**——`playerdb.build_db` 从
Liquipedia 建的选手库，外加它的人工层 `data/manual/player_overrides.json`。

两个游戏对同一份数据的用法**故意分叉**，这不是重复，是两个不同的时间点：

| | 猜选手 | Blind Draft |
|---|---|---|
| 要的是 | 这个人**是谁**（国籍、队、位置、Major 次数） | 这个人**生涯最好的样子**（玩家抽的卡）+ **现在的样子**（AI 对手） |
| 角色口径 | 生涯代表角色 | 卡是生涯代表角色；AI 对手用当前队内位置 |
| 数据源 | `players.json` | `players.json` + 5eplay 当前快照 |

`playerdb` 只提供第一列——**身份事实**。「现在打得怎么样」是 Blind Draft 自己
的事，走 `bdtools/fetch_rankings.py` 那条线，不进共享层。

> 详见 [角色与战队口径.md](角色与战队口径.md) 和
> [blind-draft/数据快照.md](blind-draft/数据快照.md)。

## 四、数据布局

`data/` 留在仓库根，因为 `data/manual/` 是**生产上的挂载卷**（管理页唯一写盘的
地方），动它就得动部署。按归属分成两半：

```
data/
  players.json           选手库（共享，playerdb.build_db 产出）
  images.json  img/      选手照片 / 队标 / 国旗（共享，playerdb.fetch_images 产出）
  hltv_top20.json        Top20 难度池      ┐
  hltv_top100.json       队伍排名快照      │ 猜选手
  hltv_player_map.json   HLTV id 映射      │
  major_results.json     Major 战绩修正    ┘
  manual/                人工层 —— 生产挂载卷，管理页写这里
    player_overrides.json  players_manual.json  images_manual.json  img/

  blind_draft/           Blind Draft 专属，整个不进猜选手镜像
    draft_cards.json       648 张选手卡（冻结，v6）
    team_snapshot.json     5eplay 当前阵容 + 位置 + 两套排名
    5e_player_stats.json   当前个人竞技数据
    5e_images.json  img/   5E 选手照片与队标（890 张，12 MB）
    vrs_global.json        官方 VRS，只做交叉核对
    major_field.json       赛场人工层
    team_roles.json  5e_aliases.json  draft_overrides.json   人工层
```

代码里**不要再写 `Path(__file__).parent.parent / "data"`**。那种写法把「我在
目录树的哪一层」焊死进了每个文件，模块一挪就集体指错，而且错得很安静（读到不
存在的路径，表现为「数据是空的」而不是报错）。统一从
[`playerdb.paths`](../packages/playerdb/paths.py) 取：

```python
from playerdb.paths import DATA, BLIND_DRAFT, MANUAL, IMG, ROOT
```

换部署布局时用环境变量 `CSTRIKLE_DATA` 顶掉，不必改代码。

## 五、怎么跑

```powershell
pip install -e .                       # 一次就行

# 猜选手
uvicorn server.main:app --host 127.0.0.1 --port 8620

# Blind Draft 调参后台（本地，改卡牌人工层）
uvicorn bdserver.main:app --host 127.0.0.1 --port 8621

# Blind Draft（命令行）
python -m blinddraft.draft             # 盲选一局
python -m blinddraft.major --seed 1    # 入场：排第几、挤掉谁
python -m blinddraft.match --selftest  # 比赛引擎的两条不变量
python -m blinddraft.ai_teams          # AI 赛场 32 队名单

# 数据维护（都是本地工具，不进镜像）
python -m playerdb.scrape.build_db --refresh-existing   # 刷新选手库
python -m playerdb.scrape.fetch_images                  # 选手照片 / 队标 / 国旗
python -m bdtools.fetch_rankings --teams         # 5eplay 队伍快照
python -m bdtools.fetch_rankings --photos        # 5E 选手照片与队标
python -m bdtools.fetch_5e_stats                 # 当前个人竞技数据

python -m pytest                       # 140 项
```

包里的模块一律用 `-m` 起。按文件路径直接跑会因为包内相对 import 崩掉
（`ImportError: attempted relative import with no known parent package`）——
管理页触发的那几个维护子进程也是因为这个改成了 `-m`。

## 六、部署（只有猜选手上线）

镜像里只有四样东西，映射后的名字直接平铺在 `/app`：

```dockerfile
COPY packages/playerdb            ./playerdb
COPY apps/guess_the_player/server ./server
COPY apps/guess_the_player/tools  ./gtptools
COPY apps/guess_the_player/static ./static
COPY data                         ./data
```

`.dockerignore` 挡在构建上下文外的有三样：`apps/blind_draft`、`data/blind_draft`，
以及 **`packages/playerdb/scrape`**。

最后一样容易被忽略但很重要：容器是只读的、也没装 Pillow，爬虫在里面本来就跑不动。
把它拷进去不会让管理页的「数据更新」变得可用，只会让那个按钮**看起来**可用，
然后以很难看懂的方式失败。这条约束在拆包之前是靠「`.dockerignore` 里写了一行
`scraper`」实现的，拆包之后改由子包边界表达——所以爬虫必须待在
`playerdb.scrape` 里，别往上挪。

两边各有权威源，别搞反：

- **生成物**（`players.json`、`images.json`、`img/`）由本地爬虫产出，随镜像发布；
- **人工层**（`data/manual/`）以线上为准，挂可写卷，管理页直接改，不用重新部署。

## 七、测试怎么分

| 位置 | 管什么 |
|---|---|
| `tests/` | 跨包的仓库级不变量：依赖方向、包映射与目录一致 |
| `packages/playerdb/tests/` | 建库爬虫、Major 战绩合并 |
| `apps/guess_the_player/tests/` | 服务端、管理页、AI 对手、solver、选手库查询 |
| `apps/blind_draft/tests/` | 卡库、设计文档里那个 SPEC 块不许和代码漂移、调参后台的推导与校验、AI 页三列的口径 |

`pytest` 从仓库根跑，四个目录都在 `pyproject.toml` 的 `testpaths` 里。

测试目录里没有 `__init__.py`，所以**测试文件的基名必须全仓库唯一**——
两个 `test_admin.py` 会让 pytest 在收集阶段直接报 import file mismatch，
而不是安静地只跑其中一个。
